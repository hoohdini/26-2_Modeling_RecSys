## 2. 등분 기준을 왜 "리뷰 건수 + 날짜 스냅"으로 바꿨나 — 원리

### 문제: 달력 균등 분할은 이 데이터에서 초기 윈도우를 텅 비게 만듦

전체 기간(2002-06-12 ~ 2014-07-23)을 달력상 균등한 기간으로 나누면, 리뷰가 2013년에 쏠려 있어서 앞쪽 윈도우에 데이터가 거의 안 들어갑니다. 원래 방식으로 만들면 train이 75건(W3)까지 떨어져 학습이 안 됐습니다.

### 그렇다고 "리뷰 인덱스로 그냥 자르기"도 안 되는 이유

이 데이터의 타임스탬프는 **날짜 단위**입니다(초 단위 없음). 고유 날짜가 2,927개뿐이고 하루에 많으면 634건이 몰려 있습니다. 리뷰를 시간순으로 세워놓고 "39,700번째까지 train"처럼 인덱스로 자르면, **같은 날짜의 리뷰가 train과 test로 쪼개질 수 있습니다.** 이는 LOO가 가진 결함(유저마다 커트라인이 달라 전역 시간 순서가 없음)과 같은 종류의 정보 누수입니다.

### 해결: 위치는 건수로 찾되, 실제 경계는 날짜로 스냅

```python
t = rows[int(n * i / n_windows)]['unixReviewTime']   # ① 위치는 "몇 번째 리뷰"로 찾고
bounds_ts.append(t)                                    # ② 자르는 기준은 그 리뷰의 "날짜값"으로
```

이후 필터링은 인덱스가 아니라 이 날짜값으로 합니다. 그러면 같은 날짜는 절대 쪼개지지 않고 통째로 한쪽 윈도우에 들어갑니다. 대가로 경계당 최대 634건(전체의 0.32%)이 "정확히 균등"에서 살짝 밀리지만, 실측 결과 균형에 미치는 영향은 미미했습니다(아래 §5 결과 참고).

### W3~W5 스냅샷 구조 (논문 원안 그대로)

5개로 나눈 청크(C1~C5, 시간순)에서 3개의 평가 스냅샷을 만듭니다. train은 뒤로 갈수록 누적됩니다.

```
W3 스냅샷: train=C1        val=C2   test=C3
W4 스냅샷: train=C1+C2     val=C3   test=C4
W5 스냅샷: train=C1+C2+C3  val=C4   test=C5
```

C1(=W1), C2(=W2)는 독립된 평가 스냅샷으로 쓰이지 않습니다 — W1은 앞에 train으로 쓸 데이터가 아예 없고(실측: train 0건→unseen 100%), W2는 train은 있지만(C1) val로 쓸 별도 청크가 안 남기 때문입니다. 대신 C1·C2는 각각 W3·W4·W5의 누적 train 재료로 이미 쓰이고 있습니다. 이건 임시방편이 아니라 원 논문(*Can Generative Recommendation Reach Cold Items?*, arXiv:2607.21101)이 애초에 설계한 구조와 동일합니다 — 논문도 W1·W2를 독립 평가에 쓰지 않고 딱 이 구조(W3/W4/W5만 평가, 누적 train)를 씁니다.

## 4. 산출물 3종 — 칼럼 상세 설명

세 파일은 전부 **같은 `iid`/`uid` 번호 체계**를 공유합니다 (`related_separate.pkl`도 포함).
실제로 `python preprocessing/repreprocess.py`를 돌려서 나온 값 기준입니다.

### 4-1. `Beauty_split_A.pkl` — LOO 분할 (TIGER 논문 재현/sanity check 전용)

| 키 | 자료형 | 설명 |
|---|---|---|
| `uid` | `{reviewerID(str): user_id(int)}` | 22,363명, 알파벳순 정렬 후 0부터 번호 부여 |
| `iid` | `{asin(str): item_id(int)}` | 12,101개, 알파벳순 정렬 후 0부터 번호 부여 |
| `user_seq` | `{user_id: [item_id, ...]}` | 유저별 **전체 기간**을 관통하는 시간순 구매 시퀀스 |
| `item_text` | `{item_id: str}` | 제목+브랜드(있으면)+설명(있으면)+카테고리(정렬됨) 이어붙인 텍스트. flan-t5-xl 임베딩 입력 |
| `item_graph` | `{item_id: {item_id, ...}}` | also_bought/also_viewed/bought_together 합쳐서 관계종류 구분 없이 저장 (방향: src→dst) |
| `item_salesrank` | `{item_id: {카테고리(str): 순위(int)}}` | 원본 salesRank를 iid로 재키만 함, 가공 없음 |
| `loo_train` | `{user_id: [item_id, ...]}` | 유저 시퀀스의 마지막 2개를 뺀 나머지 (시퀀스 길이 3 미만인 유저는 제외) |
| `loo_val` | `{user_id: item_id}` | 유저 시퀀스의 뒤에서 2번째 아이템 |
| `loo_test` | `{user_id: item_id}` | 유저 시퀀스의 마지막 아이템 |

실측: `loo_train`에 포함된 유저 22,363명 / 22,363명 (전원 시퀀스 길이 3 이상).

### 4-2. `Beauty_split_B.pkl` — 절대시간 분할 (콜드스타트 공식 결과용)

| 키 | 자료형 | 설명 |
|---|---|---|
| `uid`, `iid`, `user_seq`, `item_text`, `item_graph`, `item_salesrank` | (Split A와 동일) | 같은 값. `item_text`는 이제 A와 B가 **완전히 동일**함(§2 4번 버그 수정 확인됨) |
| `windows` | `{"W3"/"W4"/"W5": {...}}` | 아래 표 참고 |
| `cold_tiers` | `{"W3"/"W4"/"W5": {item_id: 등급(str)}}` | 그 윈도우의 train 구간 기준 콜드 등급. `unseen`/`very_rare`/`rare`/`normal` |
| `item_counts` | `{"W3"/"W4"/"W5": {item_id: 등장횟수(int)}}` | 등급의 원본 횟수. CRAB-SID처럼 등급이 아니라 실제 횟수가 필요한 처방을 위해 버리지 않고 같이 저장 |

`windows["W3"]` 내부 구조:

| 키 | 자료형 | 설명 |
|---|---|---|
| `train_seq` | `{user_id: [item_id, ...]}` | 이 윈도우의 train 구간에 등장한 상호작용을, 유저별로 시간순 정렬한 시퀀스 |
| `val_targets` | `{user_id: [item_id, ...]}` | val 구간에 등장한 상호작용. 한 유저가 여러 개일 수 있음(각각 독립된 예측 대상) |
| `test_targets` | `{user_id: [item_id, ...]}` | test 구간, 형태는 val과 동일 |
| `n_train_interactions` / `n_val_interactions` / `n_test_interactions` | `int` | 각 구간의 원본 상호작용(리뷰) 건수 |

|---|---|---|---|---|---|

| W4 | 79,342 | 39,728 | 39,619 | 1,918 | 3,651 |

(청크별 리뷰 수 W1~W5: 39,563 / 39,779 / 39,728 / 39,619 / 39,813 — 거의 균등)

### 4-3. `Beauty_related_separate.pkl` — 관계종류 보존 그래프 (보너스 검증용)

| 키 | 자료형 | 설명 |
|---|---|---|
| `iid` | `{asin(str): item_id(int)}` | Split A/B와 동일한 매핑 |
| `item_graph_detailed` | `{item_id: {item_id: {관계종류(str), ...}}}` | 두 아이템이 **어떤 관계로** 연결됐는지까지 보존. 예: `{11137: {'also_bought', 'also_viewed'}}` — 두 관계 모두로 연결됨을 의미 |

메인 실험(G-SID 기본형)에서는 관계 3종을 합친 `item_graph`(Split A/B에 포함)를 쓰고, 이 파일은 **관계별로 다른 가중치를 주는 실험**(§4의 "합쳐서 vs 절충안" 비교, `bought_together`/`also_bought`/`also_viewed`에 다른 신뢰도를 주는 식)을 할 때만 별도로 불러 쓰면 됩니다.

실측: 그래프에 등장하는 아이템 11,903 / 12,101 (고립 노드 198개), 관계 라벨 합계 403,716개 — 기존 `docs/HANDOFF_graph_sid.md`에 기록된 수치와 정확히 일치.

## 5. 실행 방법

```bash
python preprocessing/repreprocess.py
```

원본 `Data/*.json.gz`만 있으면 되고, 이미 만들어진 pkl은 참조하지 않습니다. 결과는 `preprocessing/output/`에 저장되며, `.gitignore`의 `*.pkl` 규칙에 걸려 커밋되지 않으니 팀원 각자 로컬에서 돌려서 재현하면 됩니다. 처리 시간은 로컬 기준 약 50초(대부분 `meta_Beauty.json.gz`의 `ast.literal_eval` 파싱).
