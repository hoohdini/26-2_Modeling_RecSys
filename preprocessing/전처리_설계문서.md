### 1. `uid` / `iid` — 정렬 후 정수 매김

**무엇**: `"B00KHGIMD6"` 같은 아마존 상품코드를 `0, 1, 2, 3...` 숫자로 바꿉니다.

**왜 숫자로?** 모델은 글자를 못 먹습니다. 숫자만 먹어요. 그리고 글자는 자리를 많이 차지하고 느립니다.

**왜 하필 정렬해서?** 여기가 진짜 이유입니다.

파이썬의 `set`은 **순서가 없는 주머니**예요. 구슬을 넣어두고 하나씩 꺼내면 꺼내는 순서가 매번 다릅니다. 그냥 주머니에서 나오는 대로 번호를 매기면,

- 오늘 돌림: 립스틱 = 5번
- 내일 돌림: 립스틱 = 8,341번

이렇게 됩니다. 그러면 **어제 만든 결과랑 오늘 만든 결과를 비교할 수가 없어요.** "5번 상품이 추천됐다"는데 5번이 어제랑 오늘 다른 물건이니까요.

`sorted()`로 알파벳순 줄을 세우면 언제 돌려도 립스틱은 항상 같은 번호입니다.

**비유**: 반 아이들한테 번호 매기기. 아무나 손드는 대로 매기면 매년 번호가 바뀝니다. 가나다순으로 매기면 몇 년이 지나도 김민수는 항상 3번이에요.

### 2. `orig_order` — 파일에 나온 순서 기록

**무엇**: 리뷰가 파일에서 몇 번째 줄에 있었는지를 같이 적어둡니다.

**왜?** 아마존 데이터에는 **날짜만 있고 시각이 없습니다.** "2014년 3월 5일"이 끝이에요. 몇 시 몇 분에 샀는지가 없습니다.

그래서 같은 날 세 개를 사면 **셋 다 시간이 완전히 똑같습니다.** 실제로 재보니 **유저 안에서 39%가 이런 동점**이었어요. 열 개 중 네 개꼴입니다.

시간이 같으면 뭐가 먼저인지 알 수 없죠. 이때 파일 순서를 두 번째 기준으로 쓰면 "적어도 항상 같은 순서"가 보장됩니다.

**솔직히 덧붙이면** — 지금 코드에서는 사실 이게 없어도 결과가 같습니다. 파이썬 `sort`는 동점일 때 원래 순서를 유지하거든요. 하지만 **누군가 나중에 판다스로 다시 짜면 바로 깨집니다** (판다스 기본 정렬은 동점 순서를 보장하지 않아요). 그래서 "우연히 되는 것"에 기대지 말고 **의도를 코드에 적어둔 것**입니다. 안전벨트예요.

### 3. `user_seq` — 사람별로 모아서 시간순 줄세우기

**무엇**: 원본은 리뷰가 뒤죽박죽입니다.

```
철수-샴푸, 영희-립스틱, 철수-린스, 민수-향수, 영희-마스카라...
```

이걸 사람별로 모으고 시간순으로 정리합니다.

```
철수: [샴푸, 린스, 헤어오일]
영희: [립스틱, 마스카라, 아이라이너]
```

**왜?** 추천의 목적이 **"이 사람이 다음에 뭘 살까"**를 맞추는 거니까요. 그러려면 지금까지 뭘 샀는지를 **순서대로** 알아야 합니다.

**순서가 왜 중요하냐면** — `샴푸 → 린스`와 `린스 → 샴푸`는 다른 이야기예요. 앞의 사람은 머리 감기 세트를 갖춰가는 중이고, 뒤의 사람은... 뭐 아무튼 다른 패턴입니다. 모델은 이 순서 패턴을 보고 다음을 예측합니다.

### 4. `item_graph` — 관계 3종 합치고, 명단에 없는 건 지우기

**무엇**: 메타데이터에 이런 게 들어 있습니다.

- `also_bought`: 이거 산 사람이 같이 산 것
- `also_viewed`: 이거 본 사람이 같이 본 것
- `bought_together`: 아예 묶어서 판 것

세 개를 한 덩어리로 합쳐서 "이 상품과 연결된 상품들" 목록을 만듭니다.

**왜 합쳤나?** 지금 단계에선 **"연결됐냐 안 됐냐"만** 필요하기 때문입니다. "같이 산 건 3점, 같이 본 건 1점" 이런 점수를 매길지는 G-SID를 설계할 때 정할 일이에요. 전처리에서 미리 정해버리면 나중에 마음이 바뀌었을 때 처음부터 다시 해야 합니다.

**왜 명단에 없는 걸 지웠나?** 메타 파일에는 상품이 **25만 개**가 있는데, 우리가 실제로 쓰는 건 **12,101개**뿐입니다. 리뷰가 5개 이상 달린 것만 골랐거든요.

그런데 관계 목록에는 25만 개 중 아무거나 들어 있습니다. 그대로 두면 "6번 상품은 30만번 상품과 연결됨"이라고 적히는데, **30만번이라는 상품은 우리 명단에 없어요.** 나중에 코드가 그걸 찾으려다 에러를 내거나, 더 나쁘면 조용히 이상한 계산을 합니다.

**비유**: 반 친구 명단을 만드는데 이미 전학 간 애 이름을 적어두면 안 되죠.

**💡 개선 제안**: 세 종류를 합쳐버리면 **되돌릴 수 없습니다.** 나중에 "also_viewed는 노이즈 같으니 빼자"가 되면 전처리를 다시 돌려야 해요. 종류별로 따로 저장해두고 합치는 건 다음 단계에서 하는 게 더 안전합니다.

### 5. `item_text` — 조건 걸고 이어붙이기

**무엇**: 상품명 + 브랜드 + 설명 + 카테고리를 한 문장으로 이어붙입니다. 이게 AI가 읽고 벡터로 만들 **재료**예요.

**왜 여러 개를 붙이나?**

- **상품명만**: 너무 짧아서 정보가 부족
- **설명만**: 화장품 설명은 죄다 비슷합니다. "부드럽고 촉촉하게 발리는", "피부에 자연스럽게 밀착되는"... 이것만 보면 립스틱인지 파운데이션인지 구분이 안 돼요.

그래서 여러 정보를 합쳐야 구분이 됩니다.

**왜 "조건부"인가? — 이게 진짜 중요합니다**

브랜드가 **절반(51%)이 비어 있어요.** 비었는데 그냥 넣으면 이런 문장이 만들어집니다.

```
"OPI 매니큐어 None 반짝이는 마감..."
                 ↑ 브랜드 자리에 빈 값
```

그러면 AI는 **"None"을 진짜 브랜드 이름으로 읽습니다.** 그리고 상품의 절반이 "None 브랜드"가 되니까, **AI가 걔네끼리 같은 회사 제품이라고 판단해서 한 서가에 몰아넣습니다.**

브랜드가 없다는 것뿐인데 립스틱과 샴푸와 향수가 "None 브랜드 3형제"로 묶이는 거예요. SID가 통째로 망가집니다. 그래서 **"브랜드가 있을 때만 넣는다"**는 조건을 건 겁니다.

### 6. `item_salesrank` — 열쇠만 바꾸고 내용은 그대로

**무엇**: `salesRank`는 `{"Beauty": 1523}` 같은 모양입니다. **숫자가 작을수록 잘 팔리는 상품**이에요(1등이 제일 인기).

"재키(re-key)"는 **열쇠만 바꾼다**는 뜻입니다. 서랍 내용물은 그대로 두고 손잡이 이름표만 `"B00KHGIMD6"`에서 `6`으로 바꾸는 거예요.

**왜 가공을 안 했나?** 순위를 "인기 점수"로 바꾸는 방법이 여러 가지거든요.

- `1 ÷ 순위`로 할까?
- 로그를 씌울까?
- 상위 몇 % 안에 드는지로 바꿀까?

지금 하나를 골라 가공해버리면, 나중에 다른 방법을 쓰고 싶을 때 **전처리를 처음부터 다시 돌려야 합니다.** 원본 그대로 두면 아무 때나 골라 쓸 수 있어요.

### 7. `loo_train/val/test` — 뒤에서부터 잘라 시험문제 만들기

**무엇**: 한 사람이 산 목록이 `[A, B, C, D, E]`라면,

| 조각 | 이름 | 역할 |
| --- | --- | --- |
| A, B, C | train | 교과서 (공부할 것) |
| D | val | 연습문제 (실력 점검용) |
| E | test | 진짜 시험 (마지막에 딱 한 번) |

**왜 마지막 걸 가리나?** "이 사람이 A, B, C, D를 샀는데 다음에 뭘 살까?" → 정답은 E. 이렇게 채점하는 거예요.

**왜 하필 이 방식?** TIGER 논문이 이렇게 했기 때문입니다. 우리가 구현을 제대로 했는지 확인하려면 **논문과 똑같은 방식으로 채점해서 비슷한 점수가 나오는지** 봐야 하니까요.

**"user_seq 정렬 이후에만 유효"란?** 순서를 안 맞춰놨으면 "마지막 것"이 진짜 마지막이 아니잖아요. 3번째로 산 걸 마지막인 줄 알고 시험문제로 쓰면 완전히 틀린 채점이 됩니다.

**3개 미만인 사람은 제외**합니다. 교과서/연습/시험으로 나눌 게 없으니까요.

### 8. `temporal_splits` — 달력에 선 긋기

**여기가 제일 중요합니다.** 7번(LOO) 방식에 큰 구멍이 있거든요.

**LOO의 문제**: 사람마다 "마지막"이 **다른 날**입니다.

- 철수의 마지막 구매: 2013년 5월
- 영희의 마지막 구매: 2014년 6월

그러면 **철수의 시험문제(2013년 5월 상품)가 영희의 교과서 안에 이미 들어 있습니다.** 영희는 2014년까지 공부했으니까요. 시험 답을 미리 본 셈이에요.

**콜드스타트 연구에선 이게 치명적입니다.** "신규 상품을 잘 추천하는가"를 보려는데, 사람마다 기준 시점이 다르면 **"신규"라는 말 자체가 정의가 안 됩니다.**

**해결**: 사람별로 자르지 말고, **달력에 선을 하나 긋습니다.**

```
━━━━━━━━━━━━━━━━┃━━━━━━━━
   이전은 전부 교과서   ┃  이후는 전부 시험
                    2013.8.1
```

이러면 모두에게 기준 시점이 같아서, "선 이후에 처음 나온 상품 = 신규"라고 깔끔하게 말할 수 있습니다.

**왜 날짜 대신 분위수(80/85/90/95%)로 자르나?**

날짜를 직접 고르면 데이터 양이 들쭉날쭉합니다. 어떤 해는 리뷰가 많고 어떤 해는 적으니까요. "전체 리뷰의 80%가 쌓인 시점"으로 자르면 **항상 8:2로 나뉩니다.**

덤으로, 나중에 Sports나 Toys 데이터에 똑같은 규칙을 그대로 적용할 수 있어요. 날짜를 박아두면 카테고리마다 다시 정해야 합니다.

**왜 선을 세 번 긋나?** 한 번만 자르면 **그 시점이 우연히 특이했을 수도** 있어요(블랙프라이데이 직후라든가). 세 군데서 잘라보고 결과가 일관되면 믿을 만한 거죠.

### 9. `cold_tiers_per_window` — 윈도우마다 다시 세기

**무엇**: 각 상품이 "학습 구간에 몇 번 나왔나"를 세어서 등급을 매깁니다.

| 등급 | 조건 | 뜻 |
| --- | --- | --- |
| `unseen` | 0번 | 학습 때 한 번도 못 본 완전 신상 |
| `very_rare` | 3번 이하 | 거의 못 본 것 |
| `rare` | 5번 이하 | 조금 본 것 |
| `normal` | 그 외 | 충분히 본 것 |

**왜 윈도우마다 다시 세나?** **"신상"은 절대적인 게 아니라 언제 기준이냐에 따라 달라지기 때문**입니다.

2013년 6월에 나온 립스틱은,

- 2013년 7월 기준으로는 → **신상**
- 2014년 기준으로는 → **구상품**

같은 물건인데 기준 시점이 바뀌면 등급도 바뀌죠. 그래서 윈도우가 3개면 등급표도 3개 필요합니다.

**왜 등급을 나누나?** "콜드에 약하다"고 뭉뚱그리면 안 되기 때문이에요. **아예 처음 보는 상품**과 **3번 본 상품**은 난이도가 완전히 다릅니다. 나눠서 봐야 **"우리 모델은 3번 이상 본 건 괜찮은데 0번은 완전히 무너진다"** 같은 진짜 진단이 나옵니다.

**⚠️ 여기 고쳐야 할 게 있습니다** — 앞서 말씀드린 그거예요. 지금 코드는 횟수를 다 세어놓고 **등급 라벨만 남기고 원래 숫자를 버립니다.** CRAB은 그 숫자가 필요하니 같이 저장해야 합니다.

## 원본데이터 중 어떤 부분이 들어가나

`cold_tiers_per_window`는 **`reviews_Beauty_5.json.gz`의 `asin`과 `unixReviewTime`만으로** 만들어져요. 정확한 경로는:

```
reviews(asin, unixReviewTime)
   ↓ (이미 만든 temporal_splits — 분위수 컷오프로 자른 3개 윈도우)
각 윈도우의 train_rows (그 시점 이전 상호작용들)
   ↓
train_rows 안에서 asin별 등장 횟수 세기
   ↓
0회/3회이하/5회이하/그외 로 등급화
```

메타데이터(title, brand 등)는 전혀 안 쓰여요 — **순수하게 "언제, 어떤 물건이 몇 번 상호작용됐나"**라는 상호작용 기록만으로 만들어지는 거예요.

## 이 데이터로 뭘 진단할 수 있나

가장 큰 목적은 **"콜드에 약하다"는 뭉뚱그린 말을 정밀하게 쪼개서 보는 것**이에요. 예를 들어 이 등급이 없으면 그냥 "우리 모델 Recall@10이 12%다"라는 평균값 하나만 나오는데, 등급이 있으면:

- `unseen`(0회) 아이템에서 Recall@10이 0%
- `very_rare`(3회 이하)에서 Recall@10이 4%
- `normal`(충분히 봄)에서 Recall@10이 18%

**이런 식으로 쪼개서** "우리 모델이 정확히 어디서부터 무너지는지" 정밀 진단이 가능해져요. 이게 바로 Can GR Reach Cold Items 논문의 "토큰레벨 coldness taxonomy" 개념을 실제로 구현한 부분이고, 나중에 G-SID/CRAB-SID/Guided MaskGR을 적용했을 때 **"이 처방이 정확히 어느 등급을 개선했는지"**까지 추적할 수 있게 해줘요.

## **6. 분할 A(LOO) vs B(절대시간) — 용도 구분**

- **B(절대시간)** = 실험 매트릭스 ①~⑦의 **공식 결과**, 특히 콜드/롱테일 관련 모든 주장의 근거
- **A(Leave-one-out)** = TIGER 논문 재현이 정확한지 **검증용(sanity check)**으로만 사용, 콜드스타트 주장에는 미사용 (A는 유저별 독립 분할이라 다른 유저 학습데이터에 test 아이템이 이미 노출됐을 수 있어 콜드스타트 성능이 부풀려짐)

## 

**G-SID (Graph-augmented SID)** — 우리 팀이 직접 설계하는 3가지 기법 중 하나로, **"도달가능성(Reachability)" 축**을 고치는 처방이에요.

## **문제**

TIGER/GRID의 기본 SID 생성 방식은 **아이템 텍스트 임베딩끼리의 거리만** 보고 청구기호(SID)를 배정해요. 그래서 실제로 자주 같이 팔리는 물건(`also_bought` 관계)이라도 설명 글이 다르면 완전히 다른 청구기호를 받아요. 신규/비인기 아이템은 이렇게 엉뚱한 곳에 배정돼서, 추천 로봇이 애초에 "갈 수 있는 경로" 자체가 없어져요.

## **해결 방식**

SID를 만드는 RQ-KMeans 클러스터링 단계에서, 배정 기준에 **그래프 보너스 항**을 추가해요:

```
아이템 X의 배정 = 256개 군집 중,
   [X 벡터와의 거리] − λ×[X의 그래프 이웃이 그 군집에 몇 개 있나]
   이 값이 최소인 군집
```

즉 "벡터가 가까운 군집"뿐 아니라 **"also_bought로 연결된 친구들이 이미 모여있는 군집"**도 밀어주는 거예요. `λ₁`(첫 자리, 강하게)/`λ₂`(둘째 자리, 약하게)로 레벨마다 그래프 반영 강도를 다르게 줘서, 큰 방향은 그래프를 따르되 세부는 여전히 콘텐츠로 구분되게 해요

### 이 프로젝트에서 CRAB의 위치

CRAB이 최적화하는 건 **노출 형평성**(DGU, GU 격차)이지 **콜드 아이템 회수율**이 아닙니다. 그리고 논문에 **콜드스타트 실험이 아예 없습니다.** 노출 점유율이 올라가는 것과 top-10 안에 실제로 들어가는 것은 별개예요 — 비인기 아이템 전체의 노출이 골고루 5%씩 늘어도 개별 아이템의 Recall은 그대로 0일 수 있습니다.

이건 나쁜 소식이 아니라 **팀의 기여 지점**입니다. "CRAB을 콜드스타트 관점에서 최초로 평가했다"가 성립하니까요. 다만 발표에서 **"CRAB-SID를 넣었더니 Recall이 올랐다"를 기대하지 마시고**, 처음부터 Gini·coverage·GU 축에서 움직이는 것을 목표로 잡으셔야 합니다(CRAB은 **인기 토큰을 일부러 쪼개서 인기 아이템 쪽 쏠림을 줄이는** 기법입니다. 그런데 Recall이라는 지표는 **인기 아이템만 추천하면 제일 잘 나오는** 지표예요(정리노트 5.1절). 그러니까 CRAB을 넣으면 Recall이 떨어지는 게 정상입니다. **버그가 아니라 설계대로 작동한 증거예요.)** 

**3. Stage 2가 콜드스타트와 연결되는 숨은 고리입니다.**

`L_T`는 "드문 토큰의 임베딩이 학습 부족으로 망가진다"를 고칩니다. 그런데 콜드 아이템의 SID 토큰이 정확히 그 "드문 토큰"이에요. 논문은 이 연결을 안 짚었지만, 팀 입장에선 **Stage 1(분산)보다 Stage 2(정렬)가 콜드 성능에 더 기여할 가능성**이 있습니다. 재구현할 때 Stage 1/2를 반드시 **분리해서 ablation** 하시길 권합니다. 통째로 넣으면 어느 쪽이 효과를 냈는지 영영 모릅니다.

### 재구현 전에 확인해야 할 함정

**① 백본이 다릅니다.** CRAB은 LLM 기반 추천기(Qwen2-0.5B + LoRA 계열) 위에 구현됐고, 팀은 TIGER의 1,300만 파라미터 T5 인코더-디코더 위에 올립니다. `L_T`는 토큰 임베딩 테이블에 거는 정규화라 원리상 이식되지만, **효과 크기는 전혀 다를 수 있습니다.** LLM은 사전학습된 임베딩 공간이 있고 TIGER는 처음부터 학습하니까요. "재현 실패"와 "백본 차이"를 구분할 수 있게 미리 기록해두세요.
