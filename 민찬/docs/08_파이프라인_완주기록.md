## 1. 무엇을 했나

| 단계 | 내용 | 결과 |
|---|---|---|
| Step 2 | 임베딩 생성 | **건너뜀** — 데이터에 768차원이 이미 있음 |
| Step 3 | 코드북(RK-Means) 학습 | ✅ 약 3분 |
| Step 4 | SID 생성 | ✅ 15초, 12,101개 |

| 추가 | 구간별 평가 | ✅ 새로 작성 (`scripts/segment_eval.py`) |

### Step 2를 건너뛴 방법

`items/*.tfrecord.gz` 안에 `embedding` 필드(768차원)가 이미 들어 있습니다.
GRID Step 3은 TFRecord의 임베딩을 **안 읽고**, `embedding_path` 로 준 `.pt` 파일을
`torch.load` 해서 아이템 id로 인덱싱합니다. 그래서 그 `.pt` 를 직접 만들면 됩니다.

```
형식: (N, d) float32 텐서, 행 번호 = 아이템 id
근거: src/utils/tensor_utils.py:merge_list_of_keyed_tensors_to_single_tensor
스크립트: scripts/build_step2_embeddings.py
```

⚠️ 이 임베딩은 L2 노름이 정확히 1.0으로 이미 정규화돼 있습니다(sentence-transformers 계열).
Flan-T5-XL(2048차원, 정규화 없음)과는 다른 출처이므로 **성능 수치를 GRID 논문과 비교하면 안 됩니다.**
정식 재현(B안)은 여전히 Step 2부터 해야 합니다.

### GRID 코드 자체의 버그 (3건 수정함)

**⑤ 쓰기 시 상위 폴더를 안 만듭니다 → 첫 실행이 무조건 실패합니다**
```
FileNotFoundError: .../logs/train/runs/<시각>/metadata/restart_metadata.json

Hydra는 실행마다 새 타임스탬프 폴더를 만드는데,
fs.open(path, "w") 는 그 폴더를 만들어 주지 않습니다.
수정:  src/utils/file_utils.py:open_local_or_remote 에 상위 폴더 생성 추가
```

**⑥ 단일 프로세스인데도 분산 학습용 barrier를 호출합니다**
```
RuntimeError: Default process group has not been initialized

원인:  if trainer.global_rank != None:   ← 단일 프로세스도 rank가 0이라 항상 참
수정:  torch.distributed.is_initialized() 로 검사하도록 변경
       src/utils/inference_utils.py (3곳)
```

**⑥-2 🚨 데이터 셔플에 시드가 안 넘어갑니다 → 학습이 재현되지 않습니다**
```python
# src/data/loading/components/iterators.py (수정 전, 2곳)
raw_dataset = raw_dataset.shuffle(buffer_size=128)   # ← seed 인자 없음
```
```
tf.data 의 shuffle() 은 시드를 안 주면 매 실행 무작위 시드를 뽑습니다.
GRID 는 L.seed_everything(42) 로 고정하지만 이건 파이썬·NumPy·PyTorch 만 잡습니다.
데이터 로딩이 TensorFlow 라서 그대로 새어나갑니다.

수정:  shuffle(seed=...) 이 받은 시드를 인스턴스에 저장하고
       tf.data 의 shuffle(buffer_size=128, seed=self.shuffle_seed) 로 전달

검증:  수정 후 같은 명령 2회 → SID 텐서 비트 단위 완전 동일 (12,101×7, 차이 0개)
       수정 전에는 같은 명령을 다시 쳐도 결과가 달랐습니다
```

⚠️ **셔플을 끄는 것은 해결책이 아닙니다.** 아이템 id 가 인기도와 얽혀 있어서
(순위상관 −0.42) 셔플을 끄면 앞 배치에 인기 아이템만 몰립니다.
인기도 구간이 우리 연구 주제라 치명적입니다. 셔플은 켠 채로 시드만 고정해야 합니다.

> **⑥-2 가 영향이 가장 큽니다.** ⑤·⑥ 은 에러를 내며 죽지만, 이건 조용히
> 재현 불가능한 결과를 만듭니다. 실제로 실행의 20%에서 코드북이 무너졌습니다

### 실행 설정

**⑦ PyTorch 2.6+ 는 GRID 체크포인트를 못 엽니다**
```
UnpicklingError: Weights only load failed ... ItemDataloaderConfig was not an allowed global

원인:  torch.load 의 weights_only 기본값이 True로 바뀜.
       GRID는 체크포인트에 자체 데이터클래스를 절여 넣습니다.
       Lightning이 weights_only=True 를 명시해 넘기므로 기본값만 바꿔선 안 됩니다.
수정:  src/utils/torch_compat.py 추가 (로컬 체크포인트에 한해 되돌림)
```

**⑧ `num_workers=0` 이면 `timeout` 과 `persistent_workers` 도 같이 맞춰야 합니다**
```
AssertionError: _SingleProcessDataLoaderIter requires timeout == 0
→ timeout=0, persistent_workers=false 를 함께 지정
```

**⑨ trainer 설정 키가 train / inference 사이에 다릅니다**
```
Could not override 'trainer.strategy'. Key 'strategy' is not in struct
→ inference 설정에는 strategy 키가 없습니다. ++ 를 쓰면 양쪽 다 됩니다.
```

**⑩ dataloader 설정 경로가 experiment마다 다릅니다**
```
rkmeans / sem_embeds :  data_loading.datamodule.<split>_dataloader_config
tiger                :  data_loading.<split>_dataloader_config.dataloader
                        (datamodule 쪽은 이걸 참조만 합니다)
```

**⑦~⑩ 은 `scripts/grid_mac.sh` 가 자동으로 처리합니다.**

## 3. 속도 — 🚨 맥에서 TIGER 학습은 불가능합니다

| 단계 | 시간 |
|---|---|
| Step 3 코드북 학습 (30스텝) | 약 3분 |
| Step 4 SID 생성 (12,101개) | 15초 |
| Step 6 추론 (22,363명 × 10개) | 1분 32초 |
| **Step 5 TIGER 학습** | **스텝당 27초** (워커 0개, 20스텝 591초 측정) |

### ⚠️ dataloader 워커를 올리면 오히려 느려집니다

같은 조건(20스텝, 검증 없음)에서 워커 수만 바꿔 측정한 결과입니다.

```
워커 0개    20스텝 591초   →  스텝당 27초   ← 가장 빠름
워커 6개    20스텝 715초   →  스텝당 34초
워커 12개   20스텝 753초   →  스텝당 36초
```

맥은 워커 프로세스를 spawn 방식으로 띄우기 때문에, 배치가 작을 때는
프로세스를 만들고 데이터를 건네는 비용이 병렬화 이득보다 큽니다.
**`scripts/grid_mac.sh` 의 기본값 0을 그대로 두세요.**
`GRID_NUM_WORKERS` 로 올릴 수는 있지만, 맥에서는 올릴 이유가 없습니다.
(GPU 서버에서는 결과가 다를 수 있으니 거기서 다시 재야 합니다.)

> 🚨 **측정할 때 검증 주기를 반드시 확인하세요.**
> 처음에는 `val_check_interval=25` 로 돌려서 "스텝당 2.3분"이라는 값이 나왔는데,
> 검증 세트 전체를 도는 시간이 섞인 결과였습니다. 실제 학습 스텝은 27초입니다.
> 순수 학습 속도를 재려면 `trainer.val_check_interval` 을 크게 잡아야 합니다.

### 27초가 데이터 로딩인지 연산인지는 안 밝혔습니다

dataloader 만 따로 돌려 재는 스크립트를 만들려다 **접었습니다.**
GRID 의 datamodule 이 Lightning Trainer 에 묶여 있어서 단독 실행이 계속 걸렸습니다
(리졸버 등록 → trainer 스텁 → 배치가 1개만 나옴).

어느 쪽이든 **결론이 안 바뀌기 때문에** 더 파지 않았습니다.
데이터 로딩이 병목이면 파이프라인을 고쳐야 하고, 연산이 병목이면 GPU 가 필요한데,
맥에서 32만 스텝이 불가능하다는 사실은 양쪽 다 같습니다.

> 나중에 필요해지면 GPU 서버에서 재는 게 맞습니다. 거기서는 워커 설정도 달라집니다.

### 맥에서는 불가능합니다

```
GRID 기본 설정 max_steps = 320,000
320,000 × 27초 ≈ 100일
```

> **결론: Step 3·4·6 은 맥에서 개발/디버깅해도 됩니다. Step 5는 랩 GPU가 필요합니다.**
> 랩 GPU 사양 확인이 더 급해졌습니다.

## 4. 확인한 사실

### SID 충돌 (층 수 실험의 핵심 교란 요인)

L=3, 코드북 256 기준:
```
앞 3자리만으로 고유한 아이템   92.5%
같은 SID를 공유하는 최대 개수   11개
중복 제거 자릿수(+1)를 붙이면   12,101 / 12,101 전부 고유
```
`docs/03_실험_계획.md` 가 "충돌률을 반드시 같이 재야 한다"고 한 이유가 수치로 확인됩니다.
`scripts/segment_eval.py` 가 이 값을 자동으로 같이 출력합니다.

### 🚨 GRID 기본 설정은 "증강 꺼진" 쪽입니다 — 팀 공유 필요

```yaml
# configs/experiment/tiger_train_flat.yaml
labels:
  sequence_data:
    transform:
      _target_: src.data.loading.components.label_function.NextKTokenMasking
```

`label_function` 선택지는 `Identity` 와 `NextKTokenMasking` 두 개인데,
**배포된 기본값이 `NextKTokenMasking`(증강 없음)** 입니다.
GRID 논문 어블레이션은 이 차이를 42%로 보고합니다.

⚠️ 다만 "기본 설정으로 돌리면 논문 수치가 안 나온다"고 아직 단정하면 안 됩니다.
`Identity` 로 바꿔서 양쪽을 실제로 돌려 봐야 확인됩니다. **재현 검증(B안)에서 첫 번째로 확인할 항목입니다.**

### 인기도 분포 (Beauty, 학습 데이터 기준)

| 구간 | 아이템 수 | 아이템 비율 | 상호작용 | 점유율 | 등장 횟수 |
|---|---|---|---|---|---|
| HEAD | 2,414 | 19.9% | 92,759 | **60.3%** | 15~369 |
| BODY | 7,240 | 59.8% | 53,471 | 34.8% | 4~15 |
| TAIL | 2,414 | 19.9% | 7,546 | **4.9%** | 1~4 |
| UNSEEN | 33 | 0.3% | 0 | 0.0% | 0 |

**아이템 수는 같은데 상호작용은 12배 차이납니다.** 이게 우리가 줄이려는 격차입니다.

### ⚠️ leave-one-out 에도 "학습에 없는 아이템"이 33개 있습니다

`docs/03_실험_계획.md` 는 "leave-one-out이면 COLD가 없다"고 썼는데, 정확히는 **거의 없다**입니다.
학습 split이 시퀀스의 마지막 2개를 빼기 때문에, 그 두 자리에만 등장한 아이템은 학습에서 빠집니다.
33개(0.3%)는 통계를 내기엔 너무 적으므로 **진짜 COLD 실험에는 여전히 시간 기준 분할이 필요합니다.**
평가 코드에서는 이들을 `COLD` 가 아니라 `UNSEEN` 으로 따로 표시합니다.
