## 1. 왜 이걸 먼저 쟀나

연구 질문은 "층 수(L)를 줄이면 비인기 구간이 좋아지는가"입니다.
그런데 층을 줄이면 **충돌**(서로 다른 아이템이 같은 SID를 받는 일)도 같이 늘어납니다.
둘을 분리하지 않으면 성능이 떨어졌을 때 **L이 짧아서인지 충돌이 많아서인지 구별할 수 없습니다.**

충돌률은 **TIGER 학습 없이 Step 3~4 만으로** 나옵니다. 맥에서 L 하나당 몇 분이면 끝나므로,
GPU를 기다리는 동안 미리 지형을 볼 수 있습니다.

**핵심 질문:** TAIL(비인기) 아이템이 낮은 L에서 HEAD보다 더 많이 충돌하는가?
그렇다면 "L을 줄이면 TAIL이 나빠진다"의 기계적 원인이 설명됩니다.

```
설정:  Beauty · 768차원 임베딩(A안) · 코드북 너비 256 · GRID 기본 30스텝
측정:  scripts/sweep_layers.py  →  scripts/plot_layer_sweep.py
충돌 정의:  중복 제거 자릿수를 뺀 앞 L자리가 다른 아이템과 겹치는 아이템의 비율
```

## 2. 결과 ① — 충돌은 구간을 실질적으로 가리지 않습니다

**패치 후 18회(L 6개 × 시드 42·43·44)에서 TAIL과 HEAD의 충돌률 차이입니다.**

```
TAIL − HEAD   평균 +0.23%p   표준편차 0.61%p   95% 신뢰구간 [−0.11%p, +0.46%p]

검정          부호검정   양수 14/18   p = 0.031
              윌콕슨                  p = 0.038
              t검정                   p = 0.131
```

**검정끼리 엇갈립니다.** 순위 기반 검정은 "TAIL 쪽이 살짝 높다"고 하고,
t검정과 신뢰구간은 "0을 배제 못 한다"고 합니다.

그런데 **크기를 보면 논쟁이 무의미합니다.**

```
평균 차이 0.23%p  ÷  평균 충돌률 14.0%  =  상대적으로 1.6%
```

L을 하나 줄이면 충돌률이 **수 배**씩 뛰는 판에(1.5% → 5.5% → 14% → 62%),
구간 간 차이는 0.23%p 입니다. **실험 해석을 바꿀 크기가 아닙니다.**

| L | TAIL−HEAD (시드 42 / 43 / 44) |
|---|---|
| 2 | +0.08% / +0.58% / −1.53% |
| 3 | −0.37% / +1.08% / +0.70% |
| 4 | +0.66% / +0.95% / +0.54% |
| 5 | +0.08% / −0.21% / +0.12% |
| 6 | +0.12% / +0.99% / +0.04% |
| 8 | +0.04% / +0.25% / −0.04% |

### 이게 왜 좋은 소식인가

제가 처음에 세운 가설은 **사실상 틀렸습니다.**

```
가설:   비인기 아이템은 임베딩 공간에 촘촘히 몰려 있어 먼저 뭉개진다
        → 낮은 L에서 TAIL이 훨씬 많이 충돌한다
결과:   그런 큰 차이는 없다. 있어도 0.2%p 수준이다.
        방향은 TAIL 쪽이 미세하게 높은 편이지만 무시할 크기다.
```

덕분에 해석이 오히려 깔끔해집니다.

> **층 수를 줄였을 때 TAIL 성능이 떨어진다면, 그건 충돌 때문이 아닙니다.**
> 충돌은 모든 구간을 균등하게 때리므로, 구간 간 *차이*를 만들어 낼 수 없습니다.
> 다른 원인(그래디언트 기아, 분기점 억제 등)을 봐야 합니다.

⚠️ 다만 이건 **SID 생성 단계까지만** 확인한 것입니다.
같은 SID를 가진 아이템들이 실제 추천에서 어떻게 처리되는지(중복 제거 자릿수를 모델이
얼마나 잘 맞히는지)는 TIGER 학습 후에 다시 봐야 합니다.

## 3. 결과 ② — 층 수에 따른 충돌률 (패치 후 확정판)

시드 42·43·44 로 각각 돌린 결과입니다. `max_steps=300`.

| L | 충돌률 평균 | 범위 | 유효 비트 | 붕괴 실행 |
|---|---|---|---|---|
| 2 | 62.4% | 61.9~63.3% | 15.0 | 0/3 |
| 3 | 13.7% | 13.1~14.1% | 22.4 | 0/3 |
| 4 | 5.5% | 4.1~7.7% | 27.1 | 1/3 |
| 5 | 1.5% | 1.3~1.7% | 36.6 | 0/3 |
| 6 | 0.9% | 0.8~1.0% | 44.5 | 0/3 |
| 8 | 0.4% | 0.2~0.5% | 56.0 | 1/3 |

**매끄럽게 줄고, 시드 간 폭도 좁습니다.**
아이템 12,101개를 전부 구별하려면 최소 13.6비트가 필요한데,
L=2 는 15.0비트로 아슬아슬해서 62%가 충돌합니다. L=3부터 여유가 생깁니다.

### 🚨 이전 판의 결론 하나를 철회합니다

패치 **전** 데이터로는 이렇게 나왔었습니다.

```
스피어만  층 수     vs 충돌률   −0.75
스피어만  유효 비트 vs 충돌률   −0.96      ← "유효 비트가 진짜 변수다"
```

패치 **후** 18회로 다시 재면 이렇습니다.

```
스피어만  층 수     vs 충돌률   −0.988
스피어만  유효 비트 vs 충돌률   −0.986     ← 사실상 동률
```

**"층 수보다 유효 비트가 충돌률을 잘 설명한다"는 버그가 만든 착시였습니다.**
코드북이 자주·심하게 무너지던 상태에서는 L이 예측력을 잃었던 것이고,
정상적으로 학습되면 유효 비트 ≈ L × 7.4 라 둘은 거의 같은 변수입니다.

> **그래도 유효 비트는 계속 기록해야 합니다.** 둘이 갈라지는 순간이
> 정확히 "코드북이 무너진 실행"이고, 그때 L만 보면 속습니다.
> 실제로 이번 18회 중 2회가 그랬습니다.

### 참고: 패치 전에는 이랬습니다

같은 명령을 두 번 돌렸는데 곡선 모양 자체가 달랐습니다.

```
L        2       3       4       5       6       8
1차   62.8%   13.7%    3.7%    1.5%    1.1%    0.3%   ← 깔끔하게 감소
2차   63.1%   12.8%   63.3%   12.8%   72.4%    0.3%   ← L=4, 6에서 폭발
```

아래 3절 나머지는 그 원인을 추적한 기록입니다.

### 원인 — 층 붕괴입니다 (코드워드 개수로는 안 보입니다)

처음에 저는 "붕괴가 아니다"라고 판단했는데 **틀렸습니다.** 근거로 삼은 게 이거였습니다.

```
모든 실행에서 층별 코드워드를 256개 다 씁니다.  [256, 256, ...]
```

개수만 세면 멀쩡해 보입니다. 그런데 **256개를 다 쓰더라도 그중 하나가 대부분을 삼키면
그 층은 사실상 아무것도 구분하지 못합니다.** 쏠림까지 보려면 엔트로피로 재야 합니다.

> **엔트로피(비트)** = 그 층이 실제로 담고 있는 정보량.
> 256개를 고르게 쓰면 log₂256 = 8비트, 한 코드워드에 다 몰리면 0비트에 가깝습니다.
> 예를 들어 2비트는 "실질적으로 4개 코드워드만 쓰는 것"과 같습니다.

층별 비트를 보면 좋은 실행과 나쁜 실행이 확연히 갈립니다.

| L | 층별 비트 | 유효 비트 합 | 충돌률 |
|---|---|---|---|
| 4 | `[7.44, 7.44, 7.33, 7.38]` | 29.6 | **3.7%** |
| 4 | `[7.38, 3.60, 2.08, 2.66]` | 15.7 | **63.3%** |
| 5 | `[7.43, 7.40, 7.42, 7.42, 7.31]` | 37.0 | 1.5% |
| 5 | `[7.44, 7.42, 7.42, 0.65, 0.59]` | 23.5 | 12.8% |
| 6 | `[7.51, 7.38, 7.40, 7.31, 7.34, 7.24]` | 44.2 | 1.1% |
| 6 | `[7.42, 2.01, 1.73, 1.81, 1.08, 1.04]` | 15.1 | **72.4%** |

**나쁜 실행에서는 2층 이후가 통째로 무너집니다.**
잔차 양자화는 뒷 층이 앞 층의 잔차를 받아 나누는 구조라, 한 층이 무너지면
그 뒤가 거의 같은 잔차를 받아 연쇄적으로 무너집니다.

### 무너진 실행에서는 L 이 예측력을 잃습니다

패치 전 데이터에서 L=6 인데 유효 비트가 15.1 로 L=2(14.9)와 비슷해진 실행이 있었고,
충돌률도 72% vs 63% 로 비슷했습니다. **층을 6개 만들어 놨는데 2개짜리처럼 동작한 것**입니다.

이게 패치 전 상관계수가 층 수 −0.75 / 유효 비트 −0.96 으로 갈렸던 이유입니다.
패치 후에는 붕괴가 드물어져 둘 다 −0.99 수준으로 같아집니다 (위 3절 참고).

→ `scripts/sweep_layers.py` 가 `level_bits`·`effective_bits`·`n_collapsed_levels` 를
   매 실행 함께 기록합니다. **층 수만 기록하면 무너진 실행을 나중에 구별할 수 없습니다.**

### 붕괴는 간헐적입니다 — 매번 일어나지 않습니다

L=4 를 기본 설정으로 3번 더 돌려 봤습니다.

```
#1  충돌 4.3%   유효비트 29.6   붕괴층 0   [7.47, 7.40, 7.38, 7.40]
#2  충돌 8.0%   유효비트 25.5   붕괴층 1   [7.47, 3.42, 7.22, 7.43]  ← 2번째 자리만
#3  충돌 4.0%   유효비트 29.6   붕괴층 0   [7.41, 7.42, 7.43, 7.35]
```

**3회 중 2회는 멀쩡했습니다.** 앞서 본 63.3% 같은 대형 붕괴는 재현되지 않았습니다.

엔트로피를 계산한 전체 19회를 세면 이렇습니다.

```
붕괴층이 하나라도 있는 실행   4 / 19  ≈ 21%
```

**즉 "항상 무너진다"가 아니라 "다섯 번에 한 번쯤 무너진다"입니다.**
(패치 전 기준입니다. 패치 후에는 18회 중 2회 = 11% 로 줄었고, 남은 것도 경미합니다.)
그래서 한 번 돌려 보고 괜찮았다고 안심하면 안 됩니다.

### ⚠️ 4비트 기준은 느슨합니다

L=2 에서 충돌률이 63% → 86% 로 뛴 실행들의 층별 비트입니다.

```
정상   [7.44, 7.42]  →  충돌 63%
악화   [7.47, 4.99]  →  충돌 87%
       [7.43, 5.53]  →  충돌 85%
```

두 번째 자리가 7.4 → 5.0 으로 떨어졌는데, **4비트 기준에는 안 걸립니다.**
붕괴까지는 아니어도 성능은 확실히 나빠집니다.
따라서 `n_collapsed_levels` 가 0이어도 **`level_bits` 를 눈으로 봐야 합니다.**
같은 조건끼리는 자리별 비트가 비슷해야 정상입니다.

### ✅ 원인 확정 — 셔플에 시드가 안 넘어갑니다 (GRID 버그)

```python
# code/grid/src/data/loading/components/iterators.py  (수정 전)
raw_dataset = raw_dataset.shuffle(buffer_size=128)   # ← seed 인자 없음
```

`tf.data` 의 `shuffle()` 은 시드를 안 주면 **매 실행 무작위 시드**를 뽑습니다.
GRID 는 `L.seed_everything(42)` 로 시드를 고정하지만, 이건 파이썬·NumPy·PyTorch 만
잡습니다. **데이터 로딩이 TensorFlow 라서 그대로 새어나갑니다.**

**검증**
```
셔플 OFF 로 2회        →  SID 텐서 비트 단위 완전 동일
시드 전달 후 셔플 ON 2회 →  SID 텐서 비트 단위 완전 동일   ✅
두 조건끼리는 서로 다름  →  셔플이 실제로 동작 중임도 확인
```

무작위성의 원천은 이것 **하나뿐**이었습니다.

**수정** (`patches/grid_local_fixes.patch` 에 포함)
```python
self.shuffle_seed = seed                                          # shuffle() 에서 저장
raw_dataset.shuffle(buffer_size=128, seed=self.shuffle_seed)      # tf.data 에 전달
```

⚠️ **셔플을 끄는 것은 해결책이 아닙니다.**
아이템 id 가 인기도와 얽혀 있습니다 (순위상관 −0.42).
```
id     0~2,419  평균 25.9회 등장
id 9,680~12,099 평균  6.2회 등장
```
셔플을 끄면 앞 배치에 인기 아이템만, 뒤 배치에 비인기만 들어갑니다.
하필 인기도 구간이 우리 연구 주제라 치명적입니다. **셔플은 켠 채로 시드만 고정해야 합니다.**

### 왜 시드 하나가 붕괴로 이어지는가

두 가지가 겹칩니다.

**① 깊은 층은 원래부터 아슬아슬합니다.**
```
1층이 원래 크기의 62%를 걷어감 (잔차가 38%만 남음)
층별 정보량:  7.1 → 6.0 → 4.7 → 3.5 → 2.3 → 1.0 비트
```

**② 거기에 매번 다른 순서가 들어옵니다.**
신호가 충분한 앞 층은 순서가 달라도 비슷한 답에 도달하지만,
5~6층은 남은 게 거의 없어서 순서에 따라 답이 갈립니다.

```
"나눌 게 거의 없는 데이터"  ×  "매번 바뀌는 순서"  =  다섯 번에 한 번 로또
```

### 참고: "학습이 짧아서"는 아니었습니다

가설은 이거였습니다.

```
GRID 기본값:  trainer.max_steps = 30,  batch_size = 2048
아이템 12,101개  →  한 바퀴가 6배치  →  30스텝 ≈ 5에폭  (k-means 가 수렴하기엔 짧다)
```

`max_steps` 를 10배(300)로 올려 검증했습니다. **가설은 기각됐습니다.**

```
300스텝
  L=4 #1  충돌 3.9%  유효비트 29.8  붕괴 0
  L=4 #2  충돌 4.0%  유효비트 29.9  붕괴 0
  L=4 #3  충돌 4.1%  유효비트 29.9  붕괴 0
  L=6 #1  충돌 3.7%  유효비트 31.1  붕괴 2   [7.49, 7.49, 7.42, 7.44, 0.64, 0.66]  ← 여전히 무너짐
  L=6 #2  충돌 0.7%  유효비트 44.4  붕괴 0
  L=6 #3  충돌 0.9%  유효비트 44.6  붕괴 0
```

**300스텝에서도 무너집니다.** 스텝 수는 원인이 아닙니다.

### 🎁 그런데 뜻밖의 소득이 있었습니다 — 재현성이 크게 좋아집니다

무너지지 않은 실행끼리 비교하면 차이가 확연합니다.

```
L=4 충돌률
   30스텝   4.3% / 8.0% / 4.0%   범위 4.1%p
  300스텝   3.9% / 4.0% / 4.1%   범위 0.1%p   ← 40배 촘촘
```

비용은 실행당 252초 → 598초, **2.4배**입니다. 맥에서 10분입니다.

> **권장: `trainer.max_steps=300` 을 팀 표준으로 쓰세요.**
> 붕괴를 막지는 못하지만, 정상 실행끼리의 수치가 거의 같아집니다.
> L 값을 서로 비교하는 실험에서는 이 차이가 결정적입니다.
> 4.3% vs 4.0% 같은 차이가 진짜인지 잡음인지 30스텝에서는 구별할 수 없습니다.

```bash
scripts/grid_mac.sh train experiment=rkmeans_train_flat ... trainer.max_steps=300
# 또는
python scripts/sweep_layers.py ... --extra trainer.max_steps=300
```

위 결과는 시드 수정 **전**에 얻은 것입니다. 수정 후에는 같은 설정이면 결과가 항상 같으므로,
스텝 수의 효과는 "실행 간 변동"이 아니라 "수렴 품질"로만 봐야 합니다.
그래도 300스텝 권장은 유지합니다 — 시드를 고정해도 **L 값이나 데이터가 달라지면
다시 다른 코드북**이 되므로, 조건 간 비교에서는 수렴이 충분해야 합니다.

### 붕괴는 주로 뒤쪽 자리에서 일어납니다

관찰된 붕괴 5건의 위치입니다.

```
L=4  [7.38, 3.60, 2.08, 2.66]                    2·3·4번 자리 (뒤 3개)
L=5  [7.44, 7.42, 7.42, 0.65, 0.59]              4·5번 자리   (뒤 2개)
L=6  [7.42, 2.01, 1.73, 1.81, 1.08, 1.04]        2~6번 자리   (뒤 5개)
L=6  [7.49, 7.49, 7.42, 7.44, 0.64, 0.66]        5·6번 자리   (뒤 2개)
L=4  [7.47, 3.42, 7.22, 7.43]                    2번 자리만   ← 예외
```

**5건 중 4건이 뒤쪽 연속 자리입니다.** 잔차 양자화 구조를 생각하면 그럴듯합니다.
앞 층이 정보를 다 가져가면 뒤 층에 남는 잔차가 거의 0이 되고, 그 위에서 k-means 를
돌리면 의미 있는 중심점을 못 찾습니다.

⚠️ **이것도 아직 가설입니다.** 확인하려면 층별 잔차 크기를 직접 봐야 합니다
(GRID 가 `first/last_residuals_norm_ratio` 를 로그에 남기므로 대조 가능합니다).
표본도 5건뿐이라 "주로 뒤쪽"이라는 것 이상은 말할 수 없습니다.

**원인을 몰라도 실무는 됩니다.** 탐지와 폐기가 가능하기 때문입니다. 아래 4절을 보세요.

## 3-2. 🌍 다른 데이터셋에서도 같습니다 (Sports · Toys)

Beauty 하나로는 일반화를 말할 수 없어서 두 데이터셋을 더 돌렸습니다.
L ∈ {2,3,4,5} × 시드 2개 × 2 데이터셋 = 16회. 합쳐서 **34회**입니다.

| L | Beauty | Sports | Toys |
|---|---|---|---|
| 2 | 62.4% | 71.4% | 62.0% |
| 3 | 13.7% | 19.8% | 10.7% |
| 4 | 5.5% | 6.9% | 3.3% |
| 5 | 1.5% | 3.3% | 2.8% |

**세 데이터셋 모두 층 수를 따라 매끄럽게 줄어듭니다.**

### Sports 가 더 높은 이유 — 아이템이 많아서입니다

아이템이 많을수록 구별에 필요한 비트가 늘어납니다.

```
필요 비트 = log₂(아이템 수)

Beauty  12,101개 → 13.6비트    L=2 에서 유효 15.0 → 여유 +1.4 → 충돌 62.4%
Toys    11,924개 → 13.5비트    L=2 에서 유효 14.8 → 여유 +1.3 → 충돌 62.0%
Sports  18,357개 → 14.2비트    L=2 에서 유효 15.0 → 여유 +0.8 → 충돌 71.4%
                                                      ↑ 여유가 적어서 더 충돌
```

**"여유 비트"(유효 비트 − 필요 비트)로 보면 데이터셋을 섞어도 잘 맞습니다.**

```
스피어만  여유 비트 vs 충돌률   −0.981   (34회)
스피어만  유효 비트 vs 충돌률   −0.948
```

⚠️ 한 데이터셋 안에서는 두 값이 상수만큼 차이 나므로 순위가 같습니다.
**데이터셋을 섞을 때만** 여유 비트가 유리합니다.

> **실무적 의미:** 새 데이터셋에서 L 을 몇으로 잡을지 미리 가늠할 수 있습니다.
> 아이템이 10만 개면 필요 비트가 16.6 이므로, L=2(15비트)로는 부족합니다.

### 구간 간 차이도 세 데이터셋에서 일관됩니다

```
Beauty  TAIL−HEAD 평균 +0.23%p  (n=18)
Sports                  +0.31%p  (n=8)
Toys                    +0.31%p  (n=8)

통합 (n=34)   평균 +0.27%p   표준편차 0.86%p
              부호검정  양수 24/34   p=0.024
              t검정                  p=0.082
              95% 신뢰구간 [−0.02%p, +0.54%p]
```

**표본을 두 배로 늘려도 결론이 같습니다.** 방향은 세 데이터셋에서 모두 양수로
일관되므로 **아주 작은 실제 차이는 있을 가능성이 높습니다.**
다만 크기가 +0.27%p 라, L 을 하나 바꿀 때의 변화(수 배)에 비하면 무시할 수준입니다.

## 4. 실험 설계에 주는 함의

### 🔴 반드시 반영해야 할 것

```
① 셔플 시드 패치를 먼저 적용하세요
   patches/grid_local_fixes.patch
   안 하면 같은 명령을 두 번 쳐도 결과가 다릅니다. 실험이 성립하지 않습니다.

② 층 수만 기록하면 안 됩니다 — 유효 비트를 같이 남겨야 합니다
   "L=6 실험" 이라고만 적어 두면, 그게 44비트짜리였는지 15비트짜리였는지
   나중에 알 수 없습니다. 둘은 완전히 다른 실험입니다.
   scripts/sweep_layers.py 가 level_bits·effective_bits·n_collapsed_levels 를,
   scripts/segment_eval.py 가 충돌률을 자동으로 냅니다.

   🚨 코드워드 개수(256/256)는 붕괴를 못 잡습니다. 반드시 엔트로피로 보세요.

③ 시드는 3개면 충분합니다
   패치 후 시드 간 폭이 좁습니다 (L=5 는 1.3~1.7%, L=6 은 0.8~1.0%).
   L ∈ {2,3,4,5} × 3시드 = 12회. 원래 계획 그대로 갑니다.
   ✅ Step 3~4 는 맥에서 되므로, 코드북 단계 시드 선별은 GPU 없이 미리 할 수 있습니다.
```

### ✅ 지금 바로 쓸 수 있는 규칙

원인을 몰라도 붕괴는 **탐지하고 버릴 수 있습니다.** 코드에 이미 들어가 있습니다.

```
scripts/sweep_layers.py   level_bits · effective_bits · n_collapsed_levels 를 매 실행 기록
scripts/segment_eval.py   붕괴가 감지되면 평가 결과와 함께 경고를 띄움

  🚨 코드북이 무너졌습니다 — 1개 자리가 4.0비트 미만입니다 (자리 번호 [1]).
     그 자리는 SID 를 거의 구분하지 못합니다. 이 실행의 수치는 신뢰할 수 없습니다.
```

**권장 절차**
```
⓪ 셔플 시드 패치를 적용한다  ← patches/grid_local_fixes.patch. 이게 근본 해결입니다
① trainer.max_steps=300 으로 돌린다
② Step 3(코드북 학습) 후 level_bits 를 확인한다
③ 붕괴층이 있으면 그 실행은 버리고 시드를 바꿔 다시 돌린다  ← 맥에서 10분
④ 최종 보고에는 채택한 시드와 버린 시드를 함께 적는다
```

패치를 적용하면 **같은 시드 = 같은 결과**가 보장되므로, ③에서 "다시 돌린다"는
`seed` 값을 바꾼다는 뜻입니다. 패치 전에는 같은 명령을 다시 치기만 해도 달라졌습니다.

⚠️ ②는 **선택 편향**을 만듭니다. "충돌이 적은 코드북을 골랐다"가 되면 안 되므로,
버리는 기준을 **성능이 아니라 붕괴 여부로만** 두고 미리 문서에 고정해야 합니다.
성능(HR/NDCG)을 보고 고르는 순간 결과를 믿을 수 없게 됩니다.

### 🟡 나중에 볼 것

```
· 붕괴의 진짜 원인 — 뒤쪽 층의 잔차가 0에 가까워지는 것인지
  GRID 로그의 first/last_residuals_norm_ratio 를 붕괴/정상 실행끼리 대조하면 확인됩니다
· normalize_residuals=true 설정이 잔차가 작을 때 수치적으로 불안정한지
· 붕괴 발생률이 L 에 따라 다른지 (지금은 표본이 조건당 3회뿐)
```
