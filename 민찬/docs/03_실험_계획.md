# ① 구간별 평가 인프라

## 왜 필요한가

```
세 갈래(나혜팀·수민팀·민찬)가 모두
"exploration이 좋아졌다"를 증명해야 하는데
지금 팀에 그걸 잴 자가 없습니다.
```

**Ghost 사례가 이걸 보여줍니다.**
```
비인기 노출이 17배 늘었는데 (43:1 → 1.6:1)
전체 정확도는 오히려 7% 떨어졌습니다

→ 전체 평균 Recall만 보면 "성능이 나빠졌다"로만 보입니다
→ 진짜 성과가 안 보입니다
```

## 구간 정의

```
학습 데이터에서 아이템별 상호작용 수를 세고 인기순 정렬

HEAD   상위 20%
BODY   중간 60%
TAIL   하위 20%
COLD   학습 데이터에 없음  (시간 기준 분할 필요)
```

**VarLenRec 방식(20/60/20)을 씁니다.** 그쪽과 대조하기 위해서이고, Ghost의 실제 비율(18.6~19.3%)과도 거의 같아 비교 가능합니다.

### ⚠️ COLD는 leave-one-out으로는 안 생깁니다

```
leave-one-out:  모든 아이템이 학습에 등장 → COLD 없음

시간 기준 분할:  전체 타임스탬프의 90% 지점을 기준으로
                 이후에 처음 등장한 아이템 = COLD
```

**두 분할을 다 돌리는 걸 권합니다.**
```
분할 A (leave-one-out)  →  기존 논문들과 수치 비교용
분할 B (시간 기준)       →  신규 아이템 실험용
```

## 측정 항목

### 정확도 (구간별)
```
HEAD / BODY / TAIL / COLD / ALL 각각
   Recall@5, Recall@10, NDCG@5, NDCG@10
   + 샘플 수 n          ← 반드시 같이 출력
```
> COLD 구간이 20개뿐이면 그 수치는 신뢰할 수 없습니다. n을 봐야 압니다.

### 노출 (정확도만으로는 부족)
```
구간별 추천 횟수         ← Ghost의 43:1 → 1.6:1 지표
Coverage                 추천된 고유 아이템 / 전체 아이템
구간별 Coverage
Gini 계수                노출 쏠림 정도 (0=균등, 1=독점)
```

### 진단
```
환각률          카탈로그에 없는 SID 생성 비율
코드북 활용률    실제 쓰인 코드워드 / 256
충돌률          같은 SID를 갖는 아이템 비율
```

## 출력 형식

```
구간      n      HR@10    NDCG@10   노출수    Coverage
─────────────────────────────────────────────────────
HEAD    2,420    0.2841    0.1922   18,340     94.2%
BODY    7,261    0.0912    0.0588    5,120     31.7%
TAIL    2,420    0.0104    0.0061      340      8.1%
COLD      187    0.0000    0.0000        2      0.5%
─────────────────────────────────────────────────────
ALL    12,288    0.1122    0.0831   23,802     41.3%

Gini:   0.847
환각률:  3.2%   (빔 1~5위 1.1% / 6~10위 5.8%)
```

**이 표 하나가 팀 공통 자가 됩니다.**

## 구현 (예상 2~3일)

```
1. 아이템 인기도 계산 + HEAD/BODY/TAIL 분류      반나절
2. GRID 평가 코드에 구간별 집계 추가             하루
3. 시간 기준 분할 스크립트 (COLD 생성)           하루
4. 노출·Coverage·Gini·환각률 계산                반나절
```

> Ghost는 head/tail 분류 파일이 이미 있지만 (`*.head.json`, `*.tail.json`)
> 기준이 다릅니다(누적 80%). GRID용으로 새로 만들어야 합니다.

# ② 층 수 × 구간 실험

## 연구 질문

> **GRID가 발견한 "층을 늘리면 성능이 떨어진다"는 전체 평균의 결과다.**
> **구간별로 나누면 그 하락이 어디서 오는가?**

## 세 논문이 다르게 말합니다

| 논문 | 주장 | 범위 | 구간별? |
|---|---|---|---|
| **TIGER** (2023) | "길이 바꿔도 robust" | 길이 6 × 코드북 64 시도 | ❌ (수치 미제시) |
| **GRID** (2025) | "층 늘리면 하락" 3층 0.0422 → 5층 0.0396 | L ∈ {2,3,4,5} | ❌ 전체 평균 |
| **VarLenRec** (2026) | "head 짧게, tail 길게" | L ∈ {4,6,8,10} | ✅ |
| **SA²CRQ** (2026) | "head 길게, tail 짧게" | — | ✅ (반대 결론) |

```
GRID:       ●───●───●───●
            2   3   4   5

VarLenRec:              ●───────●───────●───────●
                        4       6       8      10

겹치는 구간:            L=4  하나뿐

빈 곳:      L=2,3 을 구간별로 본 사람이 없습니다
            그리고 GRID에 따르면 거기가 최적 구간입니다
```

## 가설

**H1 (재현)** — 전체 평균에서 L=3이 최적. GRID 수치와 ±5% 이내

**H2 (핵심)** — 층 수의 효과가 구간마다 반대 방향
```
HEAD:  L 늘리면 하락    (GRID가 본 것 = 대부분 head 샘플)
TAIL:  L 늘리면 상승    (VarLenRec이 본 것)
평균:  head 샘플이 압도적이라 하락으로 보임
```

**H3 (함의)** — 구간별 최적 L이 다르면, **단일 층 수를 쓰는 것 자체가 잘못**

## 🚨 반드시 통제할 교란 요인 — 충돌률

```
L이 작으면  →  표현 공간이 작아짐  →  충돌 증가

L=2, W=256  →  65,536 조합    (Beauty 아이템 1.2만이니 이론상 충분)
L=3         →  1,677만
L=5         →  1조
```

이론상 충분해도 실제 분포는 균등하지 않습니다. **VarLenRec이 "고정 길이 충돌률 12.7%"라고 보고했습니다.**

```
충돌률을 안 재면:
   "L=2가 나쁜 게 층이 적어서인가, 충돌이 많아서인가?"
   구별할 수 없습니다
```

**모든 실험에서 충돌률과 코드북 활용률을 같이 기록하세요.**

## 실험 단계

### Phase 0 — 재현 검증 (이게 전부입니다)
```
Beauty × RK-Means × L=3 × 시드 1

성공 기준 (GRID 논문 5시드 평균):
   Recall@5   0.0422
   Recall@10  0.0639
   NDCG@5     0.0277
   NDCG@10    0.0347
   ±5% 이내

실패 시 점검 순서:
   ① 슬라이딩 윈도우 증강 (label_function 설정)  ← 없으면 40% 낮게 나옴
   ② TIGER 학습 시 num_hierarchies 를 +1 했는가
   ③ 데이터 폴더명 (training/evaluation/testing)
```

### Phase 1 — 핵심
```
Beauty × L ∈ {2, 3, 4, 5} × 시드 3  =  12회
→ H2가 보이는가?
```

### Phase 2 — VarLenRec 접점
```
Beauty × L ∈ {6, 8} × 시드 3  =  6회
→ VarLenRec 범위와 겹치게

⚠️ 시퀀스 길이 주의
   히스토리 20개 × (L+1) 토큰
   L=8이면 180토큰 (GRID 기본 sequence_length=120 초과)
   → 설정 조정 필요
```

### Phase 3 — 일반화
```
+ Sports, Toys × L ∈ {2,3,4,5} × 시드 5
```

**Phase 1까지만 해도 결과가 나옵니다.**

## 결과별 해석 — 실패 시나리오가 없습니다

| 결과 | 의미 | 가치 |

| **HEAD↓ TAIL↑** | GRID의 평균이 반대 효과를 가렸다 | 🟢 가변 길이의 근거. VarLenRec 지지 |

# GPU 예산에 따른 조정

```
1회 3시간 이하  →  원래 계획 (L 4가지 × 시드 3 = 12회)
1회 6시간 이상  →  축소
                   · 시드 3 → 2
                   · L을 {3,4,5}로 (2 제외)
                   · = 6회
```

**축소해도 결론은 나옵니다.** 구간별로 방향이 갈리는지만 보면 되니까요.

## GPU 아끼는 전략

```
1단계  Mac에서 파이프라인 검증 (steps 200k → 2k)
       목적: 설치·데이터·파이프라인 통과 확인 + 1 step 소요 시간 측정
       성능 수치는 안 나와도 됨

2단계  GPU에서 재현 1회 → 정확한 소요 시간 확보

3단계  그 시간 보고 실험 규모 확정
```
