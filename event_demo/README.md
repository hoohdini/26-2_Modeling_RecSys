## 정직하게 적을 것 — 이 시험이 보여준 한계

1. **그래프가 텍스트와 거의 겹칩니다 (G0 중첩 0.93).** 연명부에는 학과·기수·경력밖에 없어 그래프도 같은 열에서 만들었습니다. Beauty·구인구직에서 G-SID 가 이긴 이유는 그래프가 텍스트에 없는 정보(함께 구매, 직업 관계)를 가져왔기 때문입니다. **행사에서는 그래프를 프로필이 아니라 상호작용(명함 교환, 세션 참석, 관심 태그 선택)에서 만들어야** G-SID 가 의미를 갖습니다. 지금 시험에서 G-SID 의 우위(동네 순도 +0.05, 배치 z +0.6)는 작고 그 출처가 새 정보가 아닙니다.
2. **49명이 완전히 같은 문장입니다** (경력이 없고 학과·기수가 같은 사람). 임베딩이 같아지므로 주소가 겹칩니다(충돌 36%). 등록 폼에 **관심 분야, 지금 하는 일, 만나고 싶은 사람** 같은 자유 문장 한 줄이 꼭 필요합니다.
3. **β₀ = 1.0 은 여기서 무너집니다.** 그래프가 촘촘해서(243명 중 이웃 중앙값 100명) 주입이 세면 39명이 한 동네로 뭉칩니다. 0.5 로 낮춰 썼습니다. Beauty 승자 파라미터는 그래프 밀도가 다르면 그대로 옮겨지지 않으며, 행사 데이터에서 다시 골라야 합니다.
4. **추천 정확도는 재지 않았습니다.** 실제 만남 로그가 없어 "이 배치가 좋았는가"는 행사 뒤 설문·교환 로그로만 확인됩니다. 이번에 확인한 것은 주소가 발급되고, 동네가 사람 눈에 말이 되며, 배치가 우연보다 뚜렷이 뭉친다는 것까지입니다.
5. 배치 목표는 **비슷한 사람끼리 모으기 + 기수·역할 섞기**로 정했습니다. 반대로 학과를 섞는 것이 목표라면 친화도 부호를 뒤집으면 됩니다. 어느 쪽이 행사 취지에 맞는지는 운영진이 정할 문제입니다.

## 5. Offer·Seek 두 SID 검증 — 캐글 CareerBuilder (2026-09-20, `05_offer_seek_kaggle.py`)

나혜 9/17 제안(사람마다 Offer-SID와 Seek-SID, 공유 코드북, 접두사 매칭)을 캐글 데이터로 검증했습니다. 2,500명, 공고 17,728개, 정답 = 마지막 지원 공고. 원문 `kaggle_offer_seek_report.txt`.

| 질문 | 결과 |
|---|---|
| Seek(지원 공고 평균)가 Offer(프로필)보다 다음 공고를 잘 맞히나 | 예. recall@10 0.042 대 0.016 (무작위 0.0006). 둘을 섞어도 Seek 단독을 못 넘음 |
| Seek를 e5 `query:` 접두사로 넣으면 나아지나 | 아니오. 0.036으로 오히려 떨어짐. Seek가 Offer와 같은 종류의 텍스트에서 나올 때는 같은 접두사(`passage:`)를 쓸 것 |
| 세 출처를 한 코드북에 그냥 섞으면 문체로 갈리나 | 예. 1계층 칸별 최다 출처 비율 0.92, query 접두사면 1.00(완전 분리). Offer-SID와 공고 SID는 접두사가 거의 안 겹침(0.001) |
| 막는 법 | 출처별 평균을 빼고 섞기(c) 또는 상대 Offer(공고)로만 코드북을 학습하고 Seek·Offer는 배정만(d). 둘 다 세 출처가 같은 칸을 쓰고, Seek-SID 1계층 일치 0.32~0.34(무작위 4.3~4.5배), 2계층 8~9배 |
| 접두사 동네로 후보를 좁혀도 되나 | 아니오. 정답이 Seek 2계층 동네 안에 있을 확률 5.7%, 동네 안 recall@10 0.020으로 전수 검색(0.042)의 절반. 점수는 벡터 전수 코사인, SID는 라벨·묶음용 |
