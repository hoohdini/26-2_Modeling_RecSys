## 0. 30초 요약

**질문이었던 것**: "TIGER 는 정확도가 EASE_R 보다 높은데, 롱테일 노출은 어떤가?"

**답**: **더 낮습니다.**

| | NDCG@10 | APLT@10 |
|---|---|---|
| TIGER (clip_L4) | **0.0384** | **0.0497** |
| EASE_R | 0.0265 | 0.0567 |
| ItemKNN | 0.0221 | **0.5952** |

TIGER 는 EASE_R 보다 정확도가 **45% 높지만**, 추천 슬롯 중 비인기 상품에 돌아가는 몫은
**오히려 12% 적습니다**. ItemKNN 과 비교하면 **12배 적습니다.**
즉 **TIGER 는 지금 인기 편향을 줄이는 게 아니라 오히려 강화하고 있습니다.**
이 프로젝트가 풀겠다고 한 문제가 실제로 존재한다는 것이 처음으로 수치로 확인됐습니다.

그리고 **그 편향은 값싸게 되돌릴 수 있습니다.** 생성 후 재정렬 다이얼(`lam`)을 달아
파레토 곡선을 그렸습니다. 후보 200개 풀 기준:

| lam | NDCG@10 | APLT@10 | 콜드 R@50 | |
|---|---|---|---|---|
| 0 (원래 TIGER) | 0.0384 | 0.0496 | 0.0427 | |
| **1** | **0.0280** | **0.3899** | 0.0691 | ← **EASE_R 을 두 축 모두에서 이김** |
| **2** | 0.0198 | **0.6842** | **0.0814** | ← ItemKNN 을 넘는 다양성 + 더 높은 콜드 |

**정확도를 27% 내주면 롱테일 노출이 7.9배가 되면서도 EASE_R 을 두 축 모두에서 이깁니다**(lam=1).
빔 폭을 50 → 200 으로 넓히는 데 드는 정확도 비용은 사실상 0 입니다(Recall@10 0.06922 → 0.06927).
→ 4절.

정확도 우위는 통계적으로도 확실합니다: NDCG@10 에서 EASE_R 대비 **+45.2%**,
CI95 [0.0097, 0.0141], p < 0.0001 (유저 22,363명 paired bootstrap).

**그런데 재정렬로 넘을 수 없는 벽이 있습니다.** 학습에 한 번도 안 나온 상품(zero-shot 43개)의
도달률은 후보 200개까지 파고들어도 **0%** 입니다. 체크포인트 4개 중 3개가 정확히 0%,
나머지 하나가 2%(43개 중 1개). **다이얼로는 해결되지 않고 생성 분포 자체를 바꿔야 합니다.**
④번 칸(MaskGR)이 노려야 할 지점이 여기입니다. → 5절.

체크포인트 4개(시드42 / 시드7 / 전수검증 / 60k)를 같은 방식으로 재평가해
**곡선 차이의 노이즈 바닥**도 재 두었습니다: 시드만 바꿔도 NDCG 가 0.0016 움직입니다.
이 기준을 넘는 것은 60k 뿐이고, 그마저 **다양성이 아니라 열화**입니다. → 6절.

## 1. 무엇이 문제였고 어떻게 풀었나

### 1-1. 막혀 있던 지점

다양성 지표는 이미 `code/evaluate.py` 에 전부 구현돼 있었습니다.
없었던 것은 **TIGER 의 추천 결과 그 자체**였습니다. 두 가지가 막고 있었습니다.

**① `src.inference`(predict_step) 산출물은 정답이 누출돼 있습니다.**

`predict_step` 은 전체 시퀀스(정답 포함)를 넣고 "그 다음"을 생성하는 실서비스 경로입니다.
정답을 가리지 않습니다. 기존 `tiger_runs/*/infer/merged_predictions.pkl` 로 재계산해 보면:

| | 학습 로그(정답 가림) | predict_step 산출물 |
|---|---|---|
| Recall@5 | 0.0444 | 0.0576 (**+30%**) |
| Recall@10 | 0.0660 | 0.0961 (**+46%**) |

**② `top_k_for_generation` 이 10 이라 @20/@50 을 계산할 수 없었습니다.**

### 1-2. 푼 방법 — `eval_step` 을 가로채는 콜백

올바른 경로는 `test_step → eval_step` 입니다. test 데이터로더가 `NextKTokenMasking` 으로
마지막 K 토큰(=정답 SID)을 마스킹해 넣어 주기 때문입니다. 다만 GRID 는 생성 결과를
지표로만 집계하고 버립니다. 그래서 그 중간 산출물을 가로채는 콜백을 만들었습니다.

**서버 GRID 는 팀원과 공유하므로 기존 파일은 한 줄도 고치지 않았습니다.**
테스트 시작 시점에 두 지점만 런타임에 감싸고, 끝나면 원상복구합니다.

| 감싼 것 | 얻는 것 |
|---|---|
| `pl_module.eval_step` | 배치의 `user_id` |
| `pl_module.evaluator` | `generated_ids`, `marginal_probs`, `labels` |

지표 집계는 원본이 그대로 수행하므로 **학습 로그 값은 전혀 달라지지 않습니다.**

새로 추가한 파일은 셋뿐이며 전부 신규입니다.

```
GRID/src/callbacks/__init__.py            (빈 파일)
GRID/src/callbacks/prediction_dumper.py   덤프 콜백
GRID/src/eval_dump.py                     학습 없이 test 만 도는 엔트리포인트
```

### 1-3. ★ `src.train train=False` 를 쓰면 안 되는 이유 (새로 발견한 함정)

`src/train.py` 의 test 블록은 **`ckpt_path` 를 설정에서 읽지 않습니다.**
`ModelCheckpoint` 콜백의 `best_model_path` 만 봅니다.

```python
ckpt_path = getattr(checkpoint_callback, "best_model_path", None)
if ckpt_path == "": ckpt_path = None
if not ckpt_path:
    command_line_logger.warning("Best checkpoint not found! Using current weights for testing...")
```

즉 `train=False test=True ckpt_path=<경로>` 로 돌리면 학습을 건너뛴 뒤
**초기화 직후의 랜덤 가중치로 평가합니다.** 경고 한 줄만 나오고 조용히 진행됩니다.
그래서 `trainer.test(..., ckpt_path=cfg.ckpt_path)` 를 명시적으로 넘기는
`src/eval_dump.py` 를 따로 두었습니다.

세 겹으로 확인했습니다.

"모델이 본 정답"과 "우리가 채점하는 정답"이 같은 것이 증명됩니다.

### 2-1. 베이스라인을 다시 계산해야 했던 이유

## 3. 핵심 결과

Split A / LOO / `tail_frac=0.5` / 유저 22,363 · 아이템 12,101

| 모델 | Recall@10 | NDCG@10 | Coverage@10 | Gini@10 | **APLT@10** | COLD-R@50 |
|---|---|---|---|---|---|---|
| **TIGER clip_L4** | **0.0692** | **0.0384** | 0.3887 | 0.9117 | **0.0497** | 0.0429 |
| EASE_R | 0.0509 | 0.0265 | 0.8370 | 0.8379 | 0.0567 | 0.0355 |
| ItemKNN | 0.0425 | 0.0221 | 0.9577 | 0.5337 | **0.5952** | **0.0702** |
| MostPopular | 0.0121 | 0.0056 | 0.0012 | 0.9992 | 0.0000 | 0.0000 |
| Random | 0.0007 | 0.0003 | 1.0000 | 0.1304 | 0.5007 | 0.0035 |

읽는 법:
- **APLT@10** — 추천 슬롯 중 롱테일(학습 인기 하위 50%) 상품에 돌아간 비율. 높을수록 좋음.
  Average Percentage of Long Tail items (Abdollahpouri et al.). 내부 키는 `tail_exposure@10`
- **Coverage@10** — 전체 12,101개 중 한 번이라도 추천된 상품 비율
- **Gini@10** — 노출 집중도. 낮을수록 고르게 퍼짐
- **COLD-R@50** — 학습 등장 5회 이하 상품이 정답일 때의 Recall@50. 다양성이 아니라 콜드 축이라
  대표축과 컷오프를 맞추지 않고 @50 그대로 둡니다

### 세 줄 요약

1. **TIGER 는 정확도에서 확실히 이깁니다** — NDCG@10 이 EASE_R 대비 +45%, ItemKNN 대비 +74%
2. **그런데 다양성에서는 EASE_R 보다도 뒤집니다** — APLT 0.0497 vs 0.0567
3. **ItemKNN 은 정확도의 58% 로 롱테일 노출 12배, 콜드 Recall 1.6배** — 정확도만 보면 안 보이던 축

### 부가 사실

- **본 상품 제외 규칙**: 고전 베이스라인은 이미 본 상품을 추천에서 뺍니다. TIGER 는 안 뺍니다.
  TIGER 목록의 2.56% 가 이미 본 상품이었고, 제외하면 NDCG@10 0.0384 → 0.0410 으로
  **올라가되 결론은 안 바뀝니다** (APLT 0.0519, 여전히 EASE_R 0.0567 보다 낮음).
- **빔 폭이 정확도를 바꿉니다**: `top_k_for_generation` 10 → 50 으로 넓히면
  같은 체크포인트인데 Recall@10 이 0.0660 → 0.0692 (+4.9%) 로 오릅니다.
  빔서치라 폭을 넓히면 상위 10개도 달라집니다. **실험 간 비교 시 빔 폭을 반드시 고정할 것.**
- **무효 SID**: 생성된 SID 중 실제 아이템에 매핑 안 되는 비율이
  top-10 에서 0.035%, top-50 에서 0.281%, top-200 에서 1.424% 로 **뒤로 갈수록 늘어납니다.**
  원리상 `should_check_prefix=True`(접두사 제약 디코딩)로 없앨 수 있지만,
  **그 경로는 GRID 버그로 실행 자체가 안 됩니다** (6-6 절).

## 4. 파레토 곡선 — AR 모델에 다이얼 달기

### 4-1. 접근: 생성 후 재정렬

TIGER 는 빔서치라 손잡이가 없어 점 하나만 찍힙니다. 그래서 **GPU 를 한 번만 쓰고**
덤프에 들어 있는 후보 50개와 그 생성확률을 인기도 페널티로 다시 정렬했습니다.

```
점수(i) = log p(i) - lam · log(1 + 학습등장횟수(i))
```

`lam=0` 이면 원래 빔서치 순서 그대로입니다. `lam` 을 훑으면 곡선 전체가 나옵니다.

### 4-3. ★ 이 다이얼의 한계 — 반드시 같이 보고할 것

- **재정렬 다이얼이지 생성 다이얼이 아닙니다.** 후보 풀(50개) 밖의 상품은
  `lam` 을 아무리 키워도 추천될 수 없습니다. 그래서 천장이 생깁니다.
  → 4-4 절에서 풀을 200개로 넓혀 **이 천장이 모델 한계가 아니라 풀 크기 때문임을 확인**했습니다.
- **@50 지표는 `lam` 에 대해 완전히 불변입니다.** 후보가 정확히 50개인데 @50 을 보면
  집합이 같고 순서만 바뀌기 때문입니다. 실제로 Recall@50 0.1557, COLD-R@50 0.0429 가
  모든 `lam` 에서 동일합니다. **후보 풀 크기와 컷오프가 같으면 재정렬 지표는 무의미합니다.**
  대표축을 @10 으로 내린 지금도 **콜드 축 COLD-R@50 은 이 곡선에서 여전히 못 씁니다** —
  콜드 축의 다이얼 반응을 보려면 4-4 절의 후보 200개 풀을 써야 합니다.
- **MaskGR 의 확산 다이얼과 같은 종류의 기여가 아닙니다.** TIGER 곡선은
  *"AR 모델에서도 재정렬만으로 이만큼은 된다"* 는 **참조선**으로 쓰는 것이 정직합니다.

| 3 | 0.0293 | 0.0149 | 0.8143 | 0.4748 | 0.0864 |
| 5 | 0.0220 | 0.0116 | 0.8944 | 0.4258 | 0.0900 |
| 8 | 0.0182 | 0.0099 | 0.9157 | 0.4109 | 0.0913 |
| 12 | 0.0170 | 0.0092 | 0.9197 | 0.4090 | 0.0914 |

**읽을 점 넷:**

1. **50개일 때의 천장(APLT 0.38)은 모델의 한계가 아니라 후보 풀의 한계였습니다.**
   200개로 넓히니 0.92 까지 갑니다. 새 천장은 lam≈8 부근입니다.
2. **lam=1 에서 EASE_R 을 압도합니다** — NDCG 0.0280 > 0.0265 이면서
   롱테일 노출은 **6.9배**(0.3899 vs 0.0567). 정확도를 잃지 않고 다양성만 얻는 구간입니다.
3. **lam=2 에서 ItemKNN 의 다양성을 넘어섭니다**(0.6842 vs 0.5952).
   다만 그 지점의 정확도는 NDCG 0.0198 로 ItemKNN(0.0221)보다 **낮습니다.**
   **즉 이 재정렬 곡선은 ItemKNN 을 지배하지는 못합니다.** 정직하게 그렇게 써야 합니다.
   대신 같은 지점에서 **콜드 Recall@50 은 0.0814 로 ItemKNN(0.0702)보다 높습니다.**
   "노출 다양성은 더 높은데 콜드 아이템도 더 잘 맞힌다"는 것이 TIGER 쪽의 차별점입니다.
4. **Coverage 는 lam=1(0.5580)에서 정점을 찍고 다시 내려갑니다.**
   페널티를 극단으로 밀면 모든 유저에게 *같은* 희귀 상품을 밀게 되어
   노출이 다시 좁아지기 때문입니다. **다양성 지표를 하나만 보면 안 되는 이유**이며,
   `tail_exposure` 와 `coverage` 를 함께 보고해야 하는 근거입니다.

**정확도 비용은 거의 없습니다**: 빔 폭 50 → 200 으로 넓혀도 Recall@10 은
0.06922 → 0.06927 로 사실상 그대로입니다. 넓힌 이득은 전부 **다이얼의 사거리**입니다.

### 4-5. 파레토 판정 (전체 비교표는 `docs/TRACK_C_비교표.md`)

| 모델 | 프론티어 | 지배당함 |
|---|---|---|
| TIGER 다이얼 곡선 (lam 0~12) | **전 지점 O** | - |
| ItemKNN | O | - |
| **EASE_R** | **X** | **TIGER lam=0.2 / 0.5 / 1 세 지점에 지배당함** |
| MostPopular | X | 사실상 전부 |
| Random | X | ItemKNN, TIGER lam≥2 |

**결론: EASE_R 은 프론티어에서 밀려납니다. ItemKNN 은 살아남습니다.**
"확산 추천을 이긴 그 선형 모델(EASE_R)"이 다양성 축을 같이 보면 더 이상 최선이 아니라는 것,
그리고 **그걸 이기는 데 TIGER 재학습이 필요 없었다는 것**(디코딩 후 재정렬만으로 충분)이
이번 트랙 C 의 결과입니다.

### 4-6. 다이얼을 하나 더 — 노출 인지 재정렬 (Coverage 문제의 해법)

4-4 의 4번 관찰(페널티를 극단으로 밀면 Coverage 가 오히려 내려간다)은 전역 인기도
페널티의 구조적 약점입니다. **모든 유저에게 똑같이** 같은 희귀 상품을 밀기 때문입니다.

그래서 유저를 순서대로 처리하면서 **이번 라운드에 이미 추천된 횟수**를 세고 그만큼 깎는
다이얼을 추가했습니다 (`code/pareto_dial.py --mode exposure`).

```
점수(i) = log p(i) - mu · log(1 + 이번_라운드_노출횟수(i))
```

| mu | NDCG@10 | APLT@10 | **Coverage@10** | **Gini@10** | COLD-R@50 |
|---|---|---|---|---|---|
| 0 | 0.0384 | 0.0496 | 0.3886 | 0.9119 | 0.0427 |
| 0.5 | 0.0353 | 0.1377 | **0.7391** | 0.7489 | 0.0535 |
| 1 | 0.0317 | 0.2132 | **0.8165** | 0.6155 | 0.0571 |
| 2 | 0.0276 | 0.2908 | 0.8398 | 0.4860 | 0.0603 |
| 4 | 0.0219 | 0.3480 | 0.8415 | 0.4048 | 0.0612 |
| 8 | 0.0162 | 0.3849 | 0.8417 | 0.3835 | 0.0617 |
| 16 | 0.0124 | 0.4057 | 0.8418 | 0.3893 | 0.0600 |

> `mu` 는 노출 카운트를 top-20 슬롯 기준으로 셉니다(`k_slot=20`). 지표만 @10 으로 읽은
> 것이고 다이얼 자체는 @20 설정 그대로입니다. `k_slot` 을 10 으로 바꾸면 다른 곡선이 됩니다.

**두 다이얼은 서로 다른 다양성을 삽니다. 하나만 쓰면 안 됩니다.**

같은 정확도(NDCG@10 ≈ 0.035)에서 비교하면:

| | APLT@10 | Coverage@10 | Gini@10 |
|---|---|---|---|
| 인기도 페널티 lam=0.5 | **0.1706** | 0.5058 | 0.8428 |
| 노출 인지 mu=0.5 | 0.1377 | **0.7391** | **0.7489** |

- **인기도 페널티**는 "비인기 상품에 슬롯을 더 준다"를 삽니다 → `tail_exposure` 가 큽니다.
- **노출 인지**는 "노출을 고르게 편다"를 삽니다 → `coverage` 와 `gini` 가 압도적으로 좋습니다.
  mu=8 에서 Gini 0.3835 로 **ItemKNN(0.5337)보다도 고르게** 퍼집니다.

파레토 축을 `tail_exposure` 로만 잡으면 인기도 페널티가 항상 이깁니다. 그래서
**7절 프로토콜에서 `coverage` 를 보조 지표로 반드시 병기하라고 한 것입니다.**

> ⚠️ 노출 인지 모드는 **유저 처리 순서에 결과가 의존하는 온라인 알고리즘**입니다.
> "유저별로 독립인 추천"이라는 가정이 깨집니다. 순서를 user_id 오름차순으로 고정해
> 재현성은 확보했지만, 발표에서는 이 성질을 반드시 밝혀야 합니다.

## 5. 도달가능성 — 재정렬로는 절대 넘을 수 없는 천장

프로젝트는 콜드 문제를 **도달가능성 / 도달확률 / 편향** 세 축으로 나눕니다.
`coverage@10` 은 재정렬로 끌어올릴 수 있는 양이지만, **생성 후보 전체의 합집합**은
재정렬이 절대 넘을 수 없는 벽입니다. 그게 도달가능성입니다 (`code/reachability.py`).

### 5-1. clip_L4 가 닿을 수 있는 카탈로그

| 후보 깊이 | 도달 상품 | 도달률 | zero-shot | few-shot | low | mid | head |
|---|---|---|---|---|---|---|---|
| top-10 | 4,702 | 38.9% | **0%** | 13% | 18% | 46% | 92% |
| top-50 | 7,720 | 63.8% | **0%** | 30% | 45% | 75% | 99% |
| top-200 | 10,193 | 84.2% | **0%** | 57% | 74% | 93% | 100% |

### 5-2. ★ 학습에 없던 상품은 구조적으로 추천되지 않습니다

**zero-shot 상품 43개는 후보 200개까지 파고들어도 도달률 0% 입니다.**
`clip_L4` / `seed7` / `fullval` 세 체크포인트 전부 0%, `60k` 만 2%(43개 중 1개)입니다.
**체크포인트를 바꿔도, 다이얼을 아무리 돌려도 해결되지 않습니다.**
디코더가 학습에서 한 번도 타깃으로 본 적 없는 SID 열을 사실상 생성하지 않기 때문입니다.

> 이것이 재정렬 다이얼의 진짜 한계입니다. 4-3 에서 말한 "후보 풀의 천장"은
> 풀을 넓혀 올릴 수 있었지만, **zero-shot 벽은 생성 분포 자체를 바꿔야 넘습니다.**
> ④번 칸(MaskGR)의 확산 다이얼이 노려야 할 지점이 바로 여기입니다.

부수적으로, **접두사 제약 디코딩(`should_check_prefix=True`)이 이 벽을 낮출 가능성이
있습니다** — 유효 SID 로만 빔을 뻗으므로 zero-shot 상품의 SID 도 후보에 남습니다.
다만 지금은 GRID 버그로 실행 자체가 안 됩니다 (6-3 절).

### 5-3. 후보 단계에서 이미 편중돼 있습니다

`clip_L4` 기준, **후보 등장 횟수의 절반을 상위 920개(7.6%) 상품이 가져갑니다.**
즉 편향은 재정렬 단계에서 생기는 게 아니라 **생성 단계에서 이미 결정돼 있습니다.**
top-200 안에 단 한 번도 안 뜨는 상품이 1,908개(15.8%)이고, 그중
zero-shot 은 43/43(100%), few-shot 은 311/726(42.8%) 입니다.

### 5-4. 노출 인지 다이얼은 도달가능한 것을 거의 다 씁니다

`clip_L4` 의 top-200 도달률은 **84.23%**(10,193개)이고,
노출 인지 다이얼 mu≥4 의 `coverage@10` 은 **0.8415~0.8418**(10,183~10,187개)에서 멈춥니다.

**즉 재정렬로 도달가능한 상품의 99.9% 를 이미 다 꺼내 쓰고 있습니다.**
컷오프를 @20 에서 @10 으로 절반으로 줄여도 이 값이 거의 안 움직인다는 점(10,190 → 10,187)이
오히려 논지를 강하게 합니다 — **슬롯을 늘려서 닿는 게 아니라, 닿을 수 있는 게 거기까지입니다.**
Coverage 를 더 올리려면 재정렬이 아니라 **생성을 바꿔야 합니다.**

그 부산물이 롱테일 노출 증가입니다. **좋은 모델에 다이얼을 다는 쪽이 두 축 모두에서 이깁니다.**

**이것이 "차이가 노이즈 수준"의 전형적인 모습입니다.**
60k 가 4개로 가장 많지만 이는 고-lam 구간에서 롱테일 노출이 높기 때문이고,
**저-lam 구간(lam=0, 0.2)은 오히려 지배당합니다** — 6-4 절이 그 이유입니다.

### 6-6. 접두사 제약 디코딩은 GRID 버그로 실행 불가 (GRID 버그 3번째)

`should_check_prefix=True` 를 켜면 첫 배치에서 즉시 죽습니다.

```
IndexError: The shape of the mask [256] at index 0 does not match
            the shape of the indexed tensor [32, 256] at index 0
  tiger_generation_model.py:305 in _beam_search_one_step
```

원인은 명확합니다. `_beam_search_one_step` 에서 첫 계층(`generated_ids is None`)일 때는
이미 `candidate_logits[:, ~valid_prefix_mask]` 로 **열**을 마스킹해 놓고,
if/else 밖의 공용 줄에서 같은 1-D 마스크로 **행**을 다시 인덱싱합니다.

```python
if generated_ids is None:
    valid_prefix_mask = self._check_valid_prefix(...)      # shape (256,)
    candidate_logits[:, ~valid_prefix_mask] = float("-inf")   # 여기서 이미 적용됨
else:
    valid_prefix_mask = ... .reshape(-1, self.num_embeddings_per_hierarchy)
candidate_logits[~valid_prefix_mask] = float("-inf")   # ← 이 줄이 else 안에 있어야 함
```

**한 줄을 `else` 안으로 들여쓰면 고쳐집니다.** 배치 크기가 코드북 크기(256)와 다르면
항상 죽으므로, 이 경로는 사실상 한 번도 실행된 적이 없다고 봐야 합니다.
서버 GRID 는 팀 공유이므로 **패치하지 않고 보고만 합니다** — 팀 결정이 필요합니다.

고치면 얻는 것: 무효 SID 제거(top-200 에서 1.4~3.6%)와, 5-2 의 **zero-shot 벽이
낮아지는지** 확인. 후자가 사실이면 트랙 C 의 핵심 발견 하나가 바뀝니다.

## 7. 트랙 C 프로토콜 (제안)

시작 문서 4-2 절의 네 질문에 대한 답입니다.

### Q1. 어떤 분할 위에서 잴 것인가 → **Split A (LOO) 재사용**

**트랙 C 는 새 분할이 아니라 새 지표 축으로 정의합니다.**

| 트랙 | 분할 | 축 |
|---|---|---|
| A | LOO | 정확도 |
| B | 절대시간 | 시간에 따른 콜드스타트 (프로토콜 미정) |
| **C** | **A 와 동일 (LOO)** | **다양성·롱테일 노출** |

근거:
- 다양성 지표는 **노출 분포 기반**이라 시간 분할이 원리적으로 필요하지 않습니다.
- Split B 는 train 이 전체의 0.04~2.62% 라 학습 자체가 불가능합니다(블로커).
  **C 를 LOO 위에 두면 이 블로커를 완전히 피합니다.**
- 고전 베이스라인과 즉시 같은 표에 놓입니다(3절이 그 결과입니다).
- Split B 가 고쳐지면 **같은 지표 코드를 그대로** 얹으면 됩니다. 버릴 게 없습니다.

### Q2. 롱테일 경계를 어디로 → **`tail_frac=0.5` 유지**

경계를 바꿔가며 실측했습니다(`code/tail_sensitivity.py` → `results/tail_sensitivity.json`).

**이 데이터의 실제 인기 분포:**

| | |
|---|---|
| 상위 20% 아이템 | 상호작용의 59.3% |
| 상위 50% 아이템 | 상호작용의 **82.4%** |
| 상호작용 80% 를 차지하는 아이템 | 상위 **45.5%** |

즉 **이 데이터의 실증적 "80/20 지점"은 상위 45.5%** 입니다. 교과서적 80/20(상위 20%)이
아닙니다. Beauty 는 아이템당 평균 11.5회·중앙값 6회로 원래 꼬리가 두꺼운 데이터입니다.
**`tail_frac=0.5`(상위 50% 가 상호작용의 82.4%)가 이 데이터의 파레토 지점과 거의 정확히
일치합니다.** 임의로 고른 값이 아니라 데이터에 맞는 값이라고 방어할 수 있습니다.

**경계별 다양성 순위:**

| tail_frac | 롱테일 크기 | 순위 |
|---|---|---|
| 0.5 | 6,051 (상호작용 17.6%) | ItemKNN > Random > EASE_R > MostPopular |
| 0.667 | 8,072 (28.1%) | ItemKNN > Random > EASE_R > MostPopular |
| 0.8 | 9,681 (40.7%) | **Random > ItemKNN** > EASE_R > MostPopular |
| 0.9 | 10,891 (56.2%) | **Random > ItemKNN** > EASE_R > MostPopular |

**실제 모델끼리의 순위(ItemKNN > EASE_R > MostPopular)는 모든 경계에서 동일합니다.**
뒤집히는 것은 Random 뿐인데, 경계를 넓힐수록 균등추천이 자동으로 유리해지기 때문입니다
(하한 참조선이지 모델이 아닙니다). **결론: 0.5 로 고정하되, 발표에는
`tail_frac` 값과 "상위 50% 가 상호작용의 82.4%" 를 반드시 명시할 것.**

### Q3. 대표 지표 → **NDCG@10 × APLT@10**

- **컷오프는 @10 으로 고정.** 정확도 파트가 Recall@5/@10 로 정해져 있으므로
  다양성 축도 같은 K 위에 놓아야 한 표에서 읽힙니다. `evaluate.py` 가 @10/@20/@50 을
  한 번에 뽑으므로 @20 병기는 비용이 0 입니다 — 부록에 넣으면 됩니다.
- **다양성 대표축의 이름은 `APLT@10`.** Average Percentage of Long Tail items
  (Abdollahpouri et al., RecSys 2017 / FLAIRS 2019). "추천 슬롯 중 비인기 상품 몫"이라
  해석이 한 문장으로 끝나고, 목록 길이가 달라도 비교됩니다.
  발표·논문에는 `APLT` 로 쓰고 내부 키(`tail_exposure`)는 코드에만 두십시오.
- **`coverage` 는 대표축으로 쓰지 말 것. 다만 반드시 병기할 것.**
  고전 베이스라인끼리 변별력이 약합니다(ItemKNN 0.9577, EASE_R 0.8370, Random 1.0).
  그런데 **다이얼을 걸면 이야기가 완전히 달라집니다** — 4-6 절에서 보듯 같은 정확도에서
  인기도 페널티는 Coverage 0.5058, 노출 인지는 0.7391 로 갈립니다.
  `APLT` 만 보면 이 차이가 통째로 안 보입니다.
- **`gini` 는 `APLT` 와 거의 같은 것을 잽니다.** 보조로만.
- **★ `aplt@k` 와 `tail_exposure@k` 는 사실상 같은 값입니다.**
  전자는 유저별 비율의 평균, 후자는 전체 슬롯 비율이라 목록 길이가 모두 같으면
  수학적으로 동일합니다. 실측에서도 소수점 4자리까지 같습니다
  (예: TIGER @10 에서 0.0497 / 0.0497). **둘을 독립 지표처럼 나란히 보고하면 안 됩니다.**
  `docs/TRACK_C_비교표.md` 는 이제 `APLT@10` 한 칼럼으로만 싣고,
  `compare_table.py` 가 매 실행마다 두 값의 최대 차이를 각주에 찍어 병합이 안전한지 확인합니다.
- **콜드 축은 `COLD_recall@50` 으로 따로.** 다양성(노출)과 콜드(정확도)는 다른 것입니다.
  **여기만 컷오프가 @50 인데 의도한 것입니다** — 콜드 아이템은 상위 10개에 거의 안 잡혀
  @10 으로 재면 대부분 0 이 됩니다. ItemKNN 이 두 축의 차이를 보여줍니다 —
  노출도 높고 콜드 Recall 도 높습니다.

### Q4. AR 모델에서 곡선을 어떻게 → **재정렬 다이얼로 참조선, 본 곡선은 MaskGR**

팀브리핑의 원래 설계(곡선의 주무대는 ④번 MaskGR)를 **유지하되**,
TIGER 도 점 하나로 두지 말고 **재정렬 참조 곡선**을 같이 그릴 것을 제안합니다.

이유:
- 비용이 거의 0 입니다. GPU 덤프 1회 + CPU 재정렬. 이미 4절에 곡선이 나와 있습니다.
- **MaskGR 곡선이 완성되기 전에도 발표에 곡선이 있습니다.** 일정 리스크가 줄어듭니다.
- MaskGR 의 다이얼 곡선을 평가할 때 **"재정렬만 해도 여기까지는 간다"** 는
  기준선이 있어야 기여를 정직하게 주장할 수 있습니다. 이게 없으면
  "확산 다이얼이 좋다"는 주장이 "다이얼이면 뭐든 좋다"와 구별되지 않습니다.

**단, 두 곡선의 성격이 다르다는 것을 표기해야 합니다.**

| | 다이얼 | 성격 |
|---|---|---|
| TIGER | 생성 후 인기도 페널티 재정렬 | 후보 풀 안에서만 움직임. **참조선** |
| MaskGR | 확산 스텝/온도 등 생성 자체 | 생성 분포를 바꿈. **기여 주장의 본체** |
