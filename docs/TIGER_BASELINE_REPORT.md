# TIGER 베이스라인 리포트 (2026-08-20)

실험표 4×2 중 **①번 칸 — 텍스트 SID × TIGER(AR)** 를 완료했습니다.
같은 SID·같은 데이터로 학습 설정만 바꿔 3회 돌렸고, 전부 전체 테스트셋 22,363명으로 평가했습니다.

---

## 1. 결과 요약

| 실행 | 학습 설정 | Recall@5 | Recall@10 | NDCG@5 | NDCG@10 |
|---|---|---|---|---|---|
| `baseline_L4` | GRID 기본값 (고정 lr 0.001) | 0.0381 | 0.0578 | 0.0243 | 0.0307 |
| `sched_L4` | + warmup 1,500 & cosine decay | 0.0429 | 0.0641 | 0.0298 | 0.0366 |
| **`clip_L4`** | **+ gradient clipping 1.0** | **0.0444** | **0.0660** | **0.0302** | **0.0372** |

### 같은 분할에서 측정한 다른 방법들과 비교

| 모델 | Recall@10 | NDCG@10 |
|---|---|---|
| Random | 0.0007 | 0.0003 |
| MostPopular | 0.0115 | 0.0054 |
| ItemKNN | 0.0399 | 0.0211 |
| EASE_R (고전 최강) | 0.0505 | 0.0262 |
| **TIGER `clip_L4`** | **0.0660** | **0.0372** |
| TIGER 논문 (Beauty) | 약 0.0648 | 약 0.0384 |

**EASE_R 대비 Recall@10 +31%, NDCG@10 +42%.**
Recall@10 기준으로는 논문 수치를 넘었고, NDCG@10 은 97% 수준입니다.

> 논문 수치는 참고용입니다. 전처리·학습 예산이 달라 직접 비교 대상이 아니며,
> **앞으로 그래프 SID·CRAB SID 의 비교 기준선은 `clip_L4` 입니다.**

## 2. 공통 설정 (세 실행 모두 동일)

| 항목 | 값 |
|---|---|
| SID | 4단계 × 코드북 256 + 충돌 구분자 1자리 = 아이템당 **5토큰** |
| 데이터 | Split A (Leave-One-Out), 유저 22,363 / 아이템 12,101 |
| 모델 | T5 인코더-디코더 4층, d_model 128, num_heads 6 (TIGER 논문 구조) |
| 학습 | 배치 256, 최대 30,000스텝, Adam lr 0.001 |
| 검증 | 1,000스텝마다, 셔플된 3,200명 (1차만 편향 표본 1,280명) |
| 체크포인트 | `val/recall@5` 최고 시점 1개 저장 → 그 모델로 전수 테스트 |
| GPU | RTX 6000 Ada 48GB 1장, 실행당 2.5~3시간 |

재현: `code/server/tiger_beauty.sh`

```bash
sbatch --export=ALL,TAG=<이름>,CLIP=1.0,MAX_STEPS=30000 --job-name=tiger_<이름> tiger_beauty.sh
```

## 3. 학습 동역학 — 주기적 진동

세 실행 모두 **성능이 올랐다가 무너지기를 반복**했습니다. 2차가 특히 규칙적이었습니다.

| 주기 | 정점 step | 정점 val recall@5 | 직후 |
|---|---|---|---|
| 1 | 7,000 | 0.1205 | 붕괴 (0.0172) |
| 2 | 14,000 | 0.1328 | 붕괴 (0.0203) |
| 3 | 21,000 | **0.1445** | 붕괴 |
| 4 | 28,000 | 0.1442 | 붕괴 |

**정확히 7,000스텝 주기**이고, 3차(클리핑)도 같은 스텝에서 같은 패턴을 보였습니다.
학습률이 커서 최적점을 지나쳐 튕겨 나갔다가 되돌아오는 양상으로 보입니다.

**이것이 결과를 망치지는 않았습니다.** 정점이 매 주기 조금씩 올라갔고(0.1205 → 0.1445),
최고 시점 체크포인트를 저장하는 구조라 최종 모델은 정점의 것입니다.
다만 **최적 체크포인트가 운에 좌우되는 면**이 있어, 안정화는 여전히 개선 여지입니다.

### 클리핑에 대한 정확한 평가

그래디언트 클리핑은 **진동의 주기를 바꾸지 못했고**, 검증 정점도 오히려 낮았습니다(0.141 vs 0.144).
그럼에도 **전수 테스트 성적은 가장 좋았습니다.** 진폭을 줄여 더 일반화되는 지점을 잡은 것으로 해석됩니다.

또한 3차의 최선 체크포인트는 **step 28,000** 으로, 30,000 예산을 거의 소진했습니다.
**아직 수렴하지 않았다는 뜻**이라 60,000스텝 실행을 진행 중입니다(2026-08-20 기준).

## 4. 설정 함정 5가지 — 다음 사람이 반드시 알아야 할 것

전부 실제로 겪은 것이며 `code/server/tiger_beauty.sh` 주석에도 남겨 두었습니다.

| # | 증상 | 원인 / 해결 |
|---|---|---|
| 1 | 차원 불일치 또는 충돌 아이템 구분 실패 | `num_hierarchies` 는 **SID 텐서의 행 수**와 같아야 함. 4단계 SID 텐서는 (5, 12101) 이므로 **NH=5**. 모델이 `codebooks.shape[0]` 에서 유도하고 데이터는 `id_map[:NH]` 로 자른다. 4로 두면 충돌 구분자가 빠진다 |
| 2 | 임베딩 인덱스 범위 초과 | `vocab_size` = NH × 코드북크기 = **1280**. GRID 는 임베딩 테이블 하나를 계층별 오프셋으로 나눠 쓴다(계층 h 의 코드 c → h×256+c). 기본값 256 이면 터진다 |
| 3 | 검증도 체크포인트도 영원히 안 생김 | 데이터셋이 `UnboundedSequenceIterable`(무한 반복) 이라 **에폭이 끝나지 않는다.** `max_epochs` 가 아니라 **스텝 기준**(`max_steps`, `val_check_interval`)으로 제어할 것 |
| 4 | `RuntimeError: generator raised StopIteration` | TFRecord 가 split 당 파일 1개라 워커 2개 이상이면 하나가 빈 이터레이터를 받는다. `num_workers=0` + `timeout=0` + `persistent_workers=false` **세트로** |
| 5 | `mismatched input '='` (hydra) | 체크포인트 파일명에 `=` 가 들어 있어(`checkpoint_epoch=000_step=018000.ckpt`) 오버라이드 파서가 죽는다. `"ckpt_path='$CKPT'"` 로 감쌀 것 |

## 5. 우리가 겪은 측정 실수 두 가지 (같은 실수 반복 방지용)

### ① 검증 표본 편향 — 지표가 부풀려졌습니다

1차는 검증에 파일 **앞쪽 1,280명**만 썼는데(`should_shuffle_rows=false`),
이들이 우연히 구매 이력이 긴 유저였습니다.

| | 시퀀스 길이 중앙값 |
|---|---|
| 앞 1,280명 (검증에 사용) | **7.0** |
| 전체 22,363명 | **5.0** |

그 결과 검증 recall@5 가 0.227 까지 나왔지만 **전수 테스트는 0.0381** 이었습니다.
2차부터 `should_shuffle_rows=true` + 3,200명으로 고쳤습니다.

> **교훈: 검증 표본은 반드시 셔플할 것.** 전수 검증도 26초면 끝나므로 아낄 이유가 없었습니다.

### ② 추론 경로로는 테스트 지표를 재현할 수 없습니다 (구조적 제약)

예측을 육안 확인하려고 `tiger_inference_flat` 으로 추론을 돌려 지표를 재계산했는데,
값이 학습 로그와 크게 달랐습니다(Recall@10 0.0961 vs 0.0660). 원인을 추적한 결과
**GRID 의 구조상 추론 경로로는 평가를 재현할 수 없습니다.**

```python
# src/models/modules/semantic_id/tiger_generation_model.py
def predict_step(self, batch: SequentialModelInputData):        # 라벨 인자가 없음
    generated_sids, _ = self.model_step(batch)

def eval_step(self, batch: Tuple[SequentialModelInputData, SequentialModuleLabelData], ...):
    ...                                                          # 라벨을 받아 마스킹된 입력 사용
```

`predict_step` 은 배치에서 **모델 입력만** 꺼내 쓰고, 정답을 가리는 처리는
`eval_step`(검증·테스트 전용)에서만 일어납니다. 즉 추론 경로는
**"전체 시퀀스를 주고 다음 아이템을 생성하라"** 는 실서비스용이지 평가용이 아닙니다.

실제로 `labels` 오버라이드를 넣어도, `masking_token` 을 학습과 같은 -1 로 맞춰도
**예측 결과가 바이트 단위로 동일**했습니다(md5 일치). 라벨이 아예 소비되지 않기 때문입니다.

| | 정답 마스킹 | 모델이 보는 것 |
|---|---|---|
| 학습 스크립트의 test 단계 (`eval_step`) | O | 마지막 아이템을 가린 시퀀스 |
| `src.inference` (`predict_step`) | **X** | 시퀀스 **전체(정답 포함)** |

**따라서 유효한 값은 학습 로그의 `test/*` 지표뿐입니다.**
추론 출력으로 지표를 계산하면 정답을 입력에 넣은 셈이 되어 부풀려집니다.

> 지표 코드를 독립 검증하려면 `eval_step` 에 후킹하거나 테스트 루프에서 예측을 덤프하도록
> 코드를 수정해야 합니다. 아직 하지 않았습니다.

### ③ `masking_token` 이 학습과 추론 config 에서 다릅니다

| config | `masking_token` |
|---|---|
| `tiger_train_flat` (test 단계가 참조) | **-1** |
| `tiger_inference_flat` | **1** |

`NextKTokenMasking` 은 마지막 K토큰을 [마스킹토큰 1개 + 패딩 K-1개]로 바꾸는데,
모델은 학습 내내 -1 을 "여기를 예측하라" 신호로 배웁니다. 1 은 실제 코드값
(계층0의 코드 1)이라 전혀 다른 입력이 됩니다.

지금은 `predict_step` 이 라벨을 안 쓰므로 영향이 없지만,
**나중에 실제 추론 서비스를 만들 때 반드시 -1 로 맞춰야 합니다.**

## 7. ⚠️ 그래프 SID / CRAB SID 담당자에게

### 학습 설정은 바꾸지 마세요

`clip_L4` 설정이 **모든 칸의 공통 레시피**입니다. SID 만 바꾸고 학습은 동일하게 가야
성능 차이를 SID 덕분이라고 말할 수 있습니다.

```bash
sbatch --export=ALL,TAG=gsid_<이름>,SID=<내 SID.pt>,NH=<레벨+1>,CLIP=1.0 \
       --job-name=tiger_gsid_<이름> ~/recsys/tiger_beauty.sh
```

레벨 수를 바꾸면 `SEQ_LEN` 도 (레벨+1)의 배수로 맞춰야 합니다 (현재 120 = 24 × 5).

### 시드 하나로는 3% 차이를 주장할 수 없습니다

2차→3차 개선폭이 Recall@5 기준 **+3.5%** 인데, 이 정도는 **시드만 바꿔도 나올 수 있는 크기**입니다.
현재 시드 변동폭을 측정 중입니다(`clip_L4_seed7`).

발표에서 "우리 방법이 +N% 좋다"를 방어하려면:
- 효과가 충분히 크거나(예: +15% 이상), 또는
- **시드 3개씩 돌려 평균±표준편차로 보고**

8칸 × 시드 3개 = 24회 학습 ≈ 72 GPU시간. GPU 2장 동시 사용 시 **약 1.5일**입니다.
