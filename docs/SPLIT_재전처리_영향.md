# 재전처리(2026-08-22)가 기존 결과에 미치는 영향

> `preprocessing/repreprocess.py` 산출물로 갈아끼웠을 때 무엇이 바뀌고 무엇이 안 바뀌는지
> **실측**한 기록입니다. 원인과 설계 근거는 `preprocessing/전처리_수정문서.md`.

---

## 결론 세 줄

1. **정확도 지표는 한 자리도 안 바뀝니다.** `loo_test` 가 22,363명 전원 동일하기 때문입니다.
2. **다양성 지표만 미세하게 움직입니다.** 롱테일 집합의 기준인 학습 등장 횟수가 달라져서인데,
   이동폭이 **노이즈 바닥의 7%** 수준이라 트랙 C 결론은 그대로 섭니다.
3. **기존 텍스트 SID 는 그대로 씁니다.** `item_text` 가 99.1% 의 아이템에서 바뀌었지만
   카테고리 단어 *순서*뿐이고, `iid` 매핑이 동일해서 **SID 가 가리키는 상품이 그대로**입니다.
   재생성은 최종 결과 직전에 하면 됩니다 — 3절.

## 1. 실측 — 같은 덤프를 구/신 Split A 로 각각 채점

모델은 그대로 두고(`clip_L4`, 옛 데이터로 학습된 것) 채점 기준만 바꿔 본 것입니다.
즉 **지표 정의가 얼마나 흔들리는지**만 재는 실험이고, 재학습 효과는 포함돼 있지 않습니다.

| 지표 | 구 Split A | 신 Split A | 차이 |
|---|---|---|---|
| Recall@10 | 0.0692 | 0.0692 | **0** |
| NDCG@10 | 0.0384 | 0.0384 | **0** |
| Coverage@10 | 0.3887 | 0.3887 | **0** |
| Gini@10 | 0.9117 | 0.9117 | **0** |
| **APLT@10** | 0.0497 | 0.0485 | **−0.0012** |
| COLD-R@50 | 0.0429 | 0.0416 | −0.0013 (대상 6,597 → 6,197) |

**APLT 이동폭 0.0012 는 노이즈 바닥(APLT@10 0.0176)의 7% 입니다.** 시드만 바꿔도
그보다 14배 크게 움직입니다. 지금까지의 트랙 C 서술은 유효합니다.

재현:

```bash
python code/tiger_to_eval.py \
  --pred tiger_runs/clip_L4/eval_dump_k50/test_predictions_rank0.pkl \
  --split Beauty_split_A.pkl --label clip_L4
```

## 3. ★ 기존 텍스트 SID 는 그대로 씁니다

`item_text` 가 바뀌었으니 SID 도 다시 만들어야 하는 것 아니냐 — **아닙니다.**

### 왜 그대로 써도 되나

SID 는 "정답"이 있는 물건이 아니라 **상품에 주소를 배정한 결과**입니다. 유효하려면 세 가지면
충분한데, 셋 다 성립합니다.

| 조건 | 확인 |
|---|---|
| 주소가 같은 상품을 가리키는가 | `iid` 매핑이 **완전히 동일**. `item_id → asin` 이 달라진 상품 **0개** |
| 모든 실험이 같은 SID 를 쓰는가 | 학습·평가·G-SID·CRAB 전부 `sid/L4/sid_tensor.pt` 하나를 씀 |
| 무엇으로 만들었는지 아는가 | flan-t5-xl 임베딩 + RQ-KMeans, 재현 명령이 문서에 있음 |

**실제로 확인했습니다.** 신 Split A 로 기존 덤프를 채점했을 때 덤프의 정답 SID 대조가
**22,363 / 22,363 전건 일치**했습니다. 지금 SID 가 신 split 위에서 정확히 동작한다는 뜻입니다.

바뀐 것은 카테고리 단어 **순서**뿐이고, 그마저 텍스트의 뒤쪽입니다 — **앞 90% (제목·브랜드·
설명)는 글자 단위로 동일**합니다. 원래 그 순서는 `set` 이 준 임의 순서였고 지금은 사전순으로
고정됐을 뿐, 어느 쪽이 "맞는" 순서인 것도 아닙니다.

### 다시 만들어야 하는 경우

| 상황 | 재생성 필요? |
|---|---|
| `iid` 가 바뀌어 item_id 가 다른 상품을 가리킴 | **필요.** 지금은 해당 없음 |
| 파이프라인을 `repreprocess.py` 부터 끝까지 재현해 **비트 단위로 같은 SID** 를 얻고 싶음 | 필요 |
| 텍스트 순서 고정이 SID 품질을 얼마나 바꾸는지 **연구 질문으로** 보고 싶음 | 필요 |
| 그 외 | **불필요** |

### 지금 다시 만들면 오히려 비쌉니다

임베딩 4분 + SID 7분은 싸지만, 그 뒤가 비쌉니다.

- **TIGER 재학습** (수 시간) — SID 가 바뀌면 기존 체크포인트가 무효
- **트랙 C 전 수치 재계산** — `results/*.json` 이 전부 다른 SID 위의 값이 됨
- **진행 중인 작업이 딸려 옴** — G-SID 는 지금 텍스트 임베딩 위에 얹고 있고, CRAB 은
  SID 를 입력으로 받습니다. 지금 갈아엎으면 두 작업이 같이 밀립니다

**권장: 지금 SID 를 그대로 유지합니다.** 재생성은 최종 결과를 내기 직전에, 파이프라인
전체를 한 번 돌려 재현성을 확보하는 목적으로 하는 편이 낫습니다. 그때도 `sid/L4_v2/` 처럼
따로 두고 라벨로 구분하십시오 — 서로 다른 SID 위의 수치를 같은 표에 올리면 안 됩니다.

> 기록: `sid/L4/sid_tensor.pt` 는 **재전처리 이전 `item_text`(카테고리 순서 미고정)** 로
> 만든 것입니다. 논문·발표에 재현 절차를 쓸 때 이 점을 한 줄 남겨야 합니다.

## 5. 코드 호환

`evaluate.py` / `tiger_to_eval.py` / `to_grid_v2.py` / `to_grid_b.py` 는
**신·구 스키마를 모두 받습니다.** 자료형과 구조를 보고 자동으로 분기하므로
옛 pkl 로 만든 명령도 그대로 돕니다.

| 바뀐 것 | 대응 |
|---|---|
| 유저 키 str → int | `evaluate.split_key_type()` 이 판별, `remap_users(..., key_type)` 이 분기 |
| `windows` list → dict | `to_grid_b.iter_windows()` 가 둘 다 순회 |
| `train_user_seq` → `train_seq` | 두 키를 모두 찾아봄 |
| `cold_tiers` 가 윈도우 안 → 최상위 | 두 위치를 모두 찾아봄 |
