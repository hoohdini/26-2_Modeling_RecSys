## 0. 왜 이 문서가 필요한가

우리는 지금까지 Amazon Beauty라는 **남이 만든 데이터**로 검증했습니다.
이제 우리가 데이터를 만듭니다. 그러면 이런 의심이 자연스럽게 따라옵니다:

> *"결과가 잘 나오게 데이터를 만든 것 아닌가?"*

이 의심은 정당합니다. 그리고 **사후에는 해명할 수 없습니다** — 결과를 본 뒤에 무엇을 하든
"결과를 보고 맞춘 것"과 구별되지 않기 때문입니다. 그래서 **사전에** 박아둡니다.

이 문서의 목적은 우리를 방어하는 게 아니라, **우리가 스스로를 속일 여지를 구조적으로 없애는 것**입니다.

| 후보 | 상태 | 배제 사유 |
|---|---|---|
| XING RecSys Challenge 2016 / 2017 | 구인구직 추천 벤치마크 (1.5M 구직자 · 1.3M 공고 · 30M 상호작용) | **현재 비공개.** 챌린지 종료 후 배포 중단 |

**선행 사례** — 같은 제약 아래 데이터를 만들어 발표한 연구가 있습니다.

- **OpenResume** (IEEE BigData 2024) — 실제 이력서 301건 + **합성 이력서 약 3,000건**을
  공개 데이터셋으로 발표. 그래프 기반 생성 + k-익명화, ESCO 직업분류로 정규화
- **Agent4Rec** (SIGIR 2024) — LLM 에이전트로 유저 행동을 시뮬레이션해 추천 평가.
  **정렬(alignment)과 이탈(deviation)을 함께 보고**하는 방식
- **Synthetic Data-Based Simulators for RecSys: A Survey** — simulation-to-reality gap을
  측정·관리하는 방법론
- **Towards Understanding Bias in Synthetic Data for Evaluation** (CIKM 2025) —
  합성 평가가 어디서 편향되는가. §5의 게이트를 두는 근거

### 채용공고를 못 쓰는 것이 왜 치명적이지 않은가

우리 사상은 **user = 채용담당자/공고, item = 후보자 프로필**입니다(§B-1).
TIGER 는 user 를 ID 와 시퀀스로만 다루고 **텍스트를 쓰지 않습니다.**
파이프라인이 요구하는 텍스트는 `item_text` = 프로필뿐이고, 공고 본문은 애초에 안 들어갑니다.

공고 실데이터가 담당하려던 두 역할은 각각 대체됩니다.

| 원래 역할 | 대체 |
|---|---|
| 직무 어휘의 현실성 | 직업정보의 `execJob` 서술 + **지식 33 / 능력 44 구조화 벡터** (오히려 더 낫습니다) |
| G3 분포 캘리브레이션 | 고용행정통계 등 별도 공개 통계 |

> **중요**: 스킬 어휘와 직업 분류를 **우리가 발명하지 않습니다.** 공공 분류체계에서 가져옵니다.
> 그래서 §3의 그래프는 "우리가 설계한 것"이 아니라 "공공 데이터에서 도출한 것"입니다.

## 3. 생성기 명세 — 무엇이 무엇에서 나오는가

```
z_i   후보자 잠재 적합도 (직업코드 임베딩 + 경력연수 + 보유 능력단위 집합)
 │
 ├─→ profile_text_i  = Template(surface_attrs_i, 난수)      ← 2026-09-15 정정: LLM 이 아니라 템플릿
 │       손실 있는 표현: 상위 스킬 2~4개만 언급, 문장 순서·표현을 프로필마다 흔든다
 │
 ├─→ surface_attrs_i = (직업코드, 능력단위 문자열, 재직 이력, 전공)
 │       └─→ item_graph = 규칙(surface_attrs)     ← z_i 를 직접 보지 않는다
 │
 └─→ p(interaction | recruiter_r, candidate_i)
        = softmax( ⟨z_i, q_r⟩ / T  +  γ·log(1 + popularity_i)  +  δ·recency_i )
```

### 3-1. 🚫 순환 금지 조항

**`item_graph`는 `z`에서 직접 파생시키지 않습니다.**

그렇게 하면 G-SID가 상호작용을 만든 잠재변수를 그대로 들여다보게 되어 **승리가 자동 보장**됩니다.
그건 실험이 아니라 동어반복입니다.

그래프는 오직 **관측 가능한 표면 속성**에서만 만듭니다:

**우선순위가 있습니다.** Beauty에서 텍스트와 겹쳐서 강등된 것이 "속성 그래프"였고
(§5 G0), 구인구직의 `same_occupation`·`skill_overlap`은 **바로 그 속성 그래프에 해당**합니다 —
프로필 텍스트에 직업명과 스킬명이 이미 글자로 들어있기 때문입니다.
그래서 **텍스트가 모르는 관계**를 1순위로 둡니다.

| 순위 | relation | 정의 | 근거 데이터 (실측 확인됨) | 텍스트와 겹칠 위험 |
|---|---|---|---|---|
| **1** | `related_occupation` | 직업 A의 관련직업으로 등재된 B | `212D01 dtlGb=1·2` 의 **`relJobList`** | 낮음 — 외부 큐레이션. **Amazon `related`의 진짜 대응물** |
| **2** | `skill_vector` | 지식 33 + 능력 44 **레벨 벡터**의 코사인 ≥ θ | `212D01 dtlGb=5` (`knwldgLvl` · `jobAblLvl`) | 낮음~중간 — **연속값**이라 임계값으로 밀도를 맞출 수 있다 |
| 3 | `career_path` | 전공 → 직업 **전이** | `213L01` + `212D01 dtlGb=3` 의 학과 필드 | 낮음 — 유사도가 아니라 방향성 |
| 4 | `same_occupation` | 동일 KECO 코드 | `212D01 dtlGb=3` 의 `kecoCd` | ⚠️ **높음** — 강등 후보 |

> **설계가 하나 좋아졌습니다.** 원래 `skill_overlap` 은 능력단위 집합의 Jaccard(이산)로
> 잡았는데, 실측해 보니 직업정보가 **지식·능력을 레벨값까지 주는 벡터**로 제공합니다.
> 연속 유사도라서 **그래프 밀도를 결과가 아니라 임계값 θ 로 맞출 수 있습니다** —
> §3-1 의 "밀도로 맞추는 것이지 결과로 맞추는 것이 아니다"를 지키기가 훨씬 쉬워집니다.

**결정은 G0이 합니다.** 네 관계를 각각 따로 재서, Beauty에서 속성 그래프를 뺀 것과
같은 기준(0.130)으로 강등 여부를 정합니다. 이 판단은 **정확도 결과를 보기 전에** 끝냅니다.

θ 와 전이 임계값은 **그래프 평균 차수가 20~30이 되도록** 맞춥니다
(Amazon Beauty: 11,903 노드 / 301,103 방향 간선, 평균 차수 ≈ 25).
**밀도로 맞추는 것이지 결과로 맞추는 것이 아닙니다.**

> 🚫 **쓸 수 없는 관계 하나** — Beauty에서 가장 좋았던 간선 중 하나는 "같은 사람이 연달아
> 산" 공동출현이었습니다. 구인구직의 대응물은 "같은 담당자가 연달아 본 후보"인데,
> **그건 우리가 생성한 상호작용에서 나옵니다.** §3-1 순환 금지에 걸리므로 쓰지 않습니다.

### 3-2. 📌 그래프가 하는 일의 한계 (오해 방지)

G-SID에서 이웃 기여분은 **이웃들의 텍스트 임베딩**에서 옵니다.
그래프는 *누가 이웃인지와 가중치만* 정합니다. "텍스트 대신 그래프 정보를 넣는" 게 아닙니다.
따라서 새 도메인에서 필요한 것도 **좋은 이웃 정의**이지 별도의 그래프 임베딩이 아닙니다.

### 3-3. 생성 비용 통제 (품질 저하 방지 장치 포함)

프로필 12,000건을 LLM으로 개별 생성하지 않습니다.

> **2026-09-15 정정 (§9)** — 아래 2·3항의 LLM 단계는 실제로 수행하지 않았습니다.
> 실제 구현은 **템플릿 문장 조합**입니다 (`data_gen/write_profile_text.py`): 문장 틀·순서·언급 스킬 수를
> 프로필마다 난수로 흔들어 12,000건 전부 고유 텍스트를 만들었습니다 (unk 0.0000%).
> LLM 재작성은 v4b 선택 항목으로 미루며, G4 인간 검수를 통과한 경우에만 채택합니다.

1. 직업코드 × 경력구간 × 지역 조합을 **프로그램으로** 샘플 (분포는 §5 G3의 실통계에 맞춤)
2. ~~조합 유형별 **시드 프로필 약 800건만 LLM 생성**~~ → 템플릿 생성으로 대체
3. ~~나머지는 속성 재조합 + LLM 재작성으로 확장~~ → 템플릿 생성으로 대체
4. **중복도 검사**: 프로필 간 임베딩 코사인 상위 1% 제거 → 텍스트 고유율 100% 로 대체 확인

**규모 목표** (Amazon Beauty와 동급 — 하이퍼파라미터를 그대로 재사용하기 위함):
아이템(프로필) 약 12,000 / 유저(담당자) 약 20,000 / 상호작용 약 200,000

## 4. 가설 — 결과를 보기 전에 적습니다

| # | 가설 | 지표 | 판정 |
|---|---|---|---|
| **H1** | 구인구직 도메인에서도 **G-SID(β₀1.0) > 텍스트 SID** | LOO NDCG@10 | 3시드 평균 차이 > **새로 측정한** 노이즈 바닥 |
| **H2** | 신규 프로필(콜드)에서 특히 개선 | `COLD_recall@50` | 3시드 방향 일치 + 바닥 초과 |
| **H3** | 다양성을 깎지 않는다 | `APLT@50` | 3시드 평균이 텍스트 대비 비열화 |
| **H4** | *(탐색적 — 주장 아님)* 노출까지의 지연 단축 | TTFE 중앙값 | **관찰만 보고.** 이번 라운드에서 주장하지 않음 |

**주 가설은 H1입니다.** H4를 탐색적으로 둔 이유: TTFE는 이번에 처음 정의하는 지표라
노이즈 특성을 모릅니다. 실험표 ⑤-5에서 다양성 σ를 20배 과소추정했던 전례가 있어,
**분산을 모르는 지표로는 주장하지 않습니다.**

### G0. 그래프 ↔ 텍스트 비중첩 · **CPU, GPU 투입 전 첫 관문**

아이템마다 **이웃 10개**를 두 방식으로 뽑고, 두 이웃 집합의 **Jaccard 평균**을 잽니다.
(① 그래프 이웃 상위 10 ② 텍스트 임베딩 최근접 10)

**측정 방법과 기준선 모두 우리 팀이 이미 Beauty에서 쓴 것**입니다
(`RecSys/팀브리핑.md` 285~330행, "상세 ① — 겹침 정도(Jaccard)가 대체 뭘 잰 건가"):

| Beauty 비교 | Jaccard | 그때의 판정 |
|---|---|---|
| **함께구매(`also_bought`) ↔ 텍스트** | **0.065** | ✅ 낮음 = 새 정보 있음 → **채택. 지금 G-SID가 쓰는 그래프** |
| 공동출현(로그) ↔ 텍스트 | 0.022 | ✅ 거의 안 겹침 |

| 함께구매 ↔ 공동출현 | 0.020 | ✅ 서로도 거의 안 겹침 → 둘 다 사용 |

**✅ 2026-08-30 — 이 검사를 코드로 고정하고 Beauty에서 재현을 마쳤습니다.**
`data_gen/graph_text_overlap.py` · 보고서 `docs/G0_비중첩.md` · 실행 35초(CPU)

계산 방식은 일치하고 **순서와 결론이 그대로 재현**됩니다. 절대값이 조금 다른 이유는
① 그래프 이웃을 10개로 자르는 규칙이 팀브리핑에 명시돼 있지 않고
② 브랜드 결측 51%를 어떻게 처리하느냐 때문입니다 (보고서에 상세).

| 이 구현으로 잰 값 | 팀브리핑 | 그때 판정 |
|---|---|---|
| 속성(같은 브랜드만) ↔ 텍스트 **0.1139** | 0.130 | ❌ 강등 |
| also_viewed ↔ 텍스트 **0.0873** | — | — |
| 관계 전체(현재 G-SID) ↔ 텍스트 **0.0743** | — | ✅ 사용 중 |
| also_bought ↔ 텍스트 **0.0722** | 0.065 | ✅ 채택 |
| bought_together ↔ 텍스트 **0.0357** | — | ✅ 채택 |
| 공동출현 ↔ 텍스트 **0.0242** | 0.022 | ✅ 채택 |

**판정선은 팀브리핑의 0.130이 아니라 같은 구현으로 잰 강등 앵커를 씁니다.**
다른 척도의 숫자를 섞으면 비교가 성립하지 않습니다.

```
Jaccard < 0.087    통과 — 채택된 그래프들이 있는 구간
0.087 ~ 0.114      주의 — 재검토 (이 구간에 also_viewed 가 있다)
Jaccard ≥ 0.114    실패 — 강등된 속성 그래프와 같은 처지. 재설계
```

- **실패 시**: GPU를 쓰지 않고 그래프 정의부터 고칩니다.
  그래프가 텍스트를 되풀이하고 있다면 G-SID가 더할 정보가 없습니다.

> ⚠️ 구인구직에서 이 함정이 Beauty보다 **더 크게 납니다.** Beauty에서 속성 그래프가
> 탈락한 이유는 제품명 `OPI Nail Lacquer`에 브랜드와 카테고리가 **이미 글자로 들어있어서**였습니다.
> 프로필 텍스트에도 직업명과 스킬명이 그대로 적혀 있으므로,
> `same_occupation`·`skill_overlap` 간선은 **텍스트와 겹칠 위험이 구조적으로 높습니다.**
> G0을 GPU 앞에 두는 이유가 이것입니다.

### G1. 그래프 무작위화 대조 · **GPU 2셀** ★

차수를 보존한 채 간선을 무작위로 재배선(degree-preserving rewiring)한 **가짜 그래프**로
전체 파이프라인을 다시 돌립니다.

- **통과 = 이득이 사라짐**
- **실패 = 이득이 남음** → 그 이득은 그래프의 의미가 아니라 다른 데서 온 것입니다.
  이 경우 **H1이 성립해도 결과를 폐기**하고 데이터 설계를 고칩니다.

### G2. 시뮬레이터 격리 검증 · **GPU 2셀** ★

**실제 Amazon Beauty**의 아이템·텍스트·그래프는 그대로 두고,
**상호작용만** 우리 시뮬레이터(§3)로 재생성합니다. 그리고 확정된 결론
("그래프 > 텍스트")이 재현되는지 봅니다.

- **통과 = 결론 방향 재현**
- 이 검사는 **실데이터 위에서** 돌기 때문에, "생성 데이터라 못 믿겠다"는 반론을
  시뮬레이터 하나로 좁혀서 답합니다.

### G3. 통계 정합성 · CPU

생성 데이터의 분포를 공공 실통계 및 Beauty와 대조합니다.

| 항목 | 대조 대상 |
|---|---|
| 직종·지역 분포 | 고용24 채용정보 실제 분포 |
| 인기도 Gini | Amazon Beauty (참고선) |
| 시퀀스 길이 분포 | Amazon Beauty (참고선) |
| 롱테일 경계 (상호작용 80% 지점) | Beauty는 상위 45.5% — `tail_frac=0.5`의 근거였음 |

**허용 구간은 생성 전에 `docs/G3_허용구간.md`에 적고 고정합니다.**

### G4. 인간 블라인드 검수 · 사람

생성 프로필–공고 매칭 쌍 **100건**을 팀원 3명이 블라인드로 평가합니다.

- 보고: 인간–시뮬레이터 일치율, 평가자 간 일치도(κ)
- **임계값을 강요하지 않습니다.** 수치 자체를 그대로 보고합니다.
  낮게 나오면 "시뮬레이터가 사람 판단과 이만큼 다르다"는 것이 결과입니다.

### G5. 부정 결과 수용 선언

**G-SID가 이 도메인에서 못 이기면 그대로 보고합니다.**
데이터를 다시 만들어 재시도하지 않습니다 (§6 참조).

## 6. 🚫 하지 않기로 하는 것

이 목록이 사전등록의 핵심입니다.

1. **결과를 본 뒤 데이터를 재생성하지 않습니다.**
   데이터셋 버전은 해시로 고정하고, 모든 결과에 데이터 해시를 함께 기록합니다.
2. **결과를 본 뒤 가설·지표·판정 기준을 바꾸지 않습니다.** (§9의 절차 없이는)
3. **결과를 본 뒤 조건을 배제하지 않습니다.**
   배제는 **데이터 속성에 근거해 사전에만** 합니다.
   *(전례: Beauty Split B의 W3는 "테스트 유저의 56.7%가 학습 이력 없음"이라는
   데이터 속성 때문에 사전 배제했고, 그 수치는 지금도 보존돼 있습니다.)*
4. **노이즈 바닥 아래 차이를 주장하지 않습니다.**
   Beauty의 바닥(0.0016 / 0.0176)을 새 데이터에 그대로 쓰지 않고 **재측정**합니다.
5. **시드 1회 결과로 다양성을 주장하지 않습니다.** APLT·커버리지는 3시드 평균만.
6. **여러 지표를 훑어 이긴 것만 고르지 않습니다.** 주 지표는 H1의 NDCG@10입니다.
7. **G1·G2를 건너뛰지 않습니다.** 결과가 좋아 보인다는 것은 건너뛸 이유가 되지 않습니다.

## 7. 사전 고정 — 승자 선택 규칙

Amazon Beauty에서 쓴 것과 **같은 형식**을 유지합니다 (구조를 바꾸면 비교가 흐려집니다).

```
제약 1   R@50    ≥ baseline(텍스트 SID)
제약 2   APLT@50 ≥ baseline(텍스트 SID)
제약 3   최저층 비트 ≥ 4.0        (코드북 붕괴 배제)
목적     위를 통과한 것 중 COLD_recall@50 최대
```

baseline 수치는 **텍스트 SID 3시드 평균을 측정한 직후 이 문서에 기입하고 고정**합니다.
